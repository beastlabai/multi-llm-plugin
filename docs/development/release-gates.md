# Makefile lanes and release gates

Read before changing the `Makefile`, a container lane target, a package gate, or a release helper.

Back to the [development guide](../../skills/multi-llm/AGENTS.md). The `Makefile` keeps one or two lines of "why" beside each recipe and points here for the rest. Every target carries a `## description` suffix, and `make help` is generated from those suffixes (`tests/test_makefile_help.py` keeps the list, the `.PHONY` line and the definitions in step). Paths beginning with `docs/`, `packaging/`, or `plans/` are repository-relative; other implementation paths are relative to `skills/multi-llm/`. Dated incidents explain the rules; verify version-specific claims against current code.

## Why the Makefile sits at the repository root

The build context of the container image is the repository root: the product under test sits above `skills/multi-llm/tests/container/`, and `COPY` cannot reach outside the context. A makefile beside the Dockerfile would spend every recipe reaching back through `../../..`, and the one flag pair that must not be mistyped (`-f <dockerfile> <repo-root>`) would be written relative to a directory nobody builds from. Every command here and in the README is a bare `make <target>` typed at the checkout root, with no `-C`.

**The Makefile owns the `docker build` invocation, the `docker version` pre-flight and each target's `pytest -m` expression. It does not own `docker run` flags.** Those are built per row by `tests/container/harness.py` from `tests/container/posture.yaml`: `--network`, `--user`, the `--tmpfs` mode strings, `--cap-drop`, `--read-only`, `--pids-limit`, the single `/work/out` bind and, on the host lane only, the one credential variable. That split is what lets the posture test inspect the run flags from both sides; a shell-quoted per-row matrix in a recipe could not be asserted against. The one exception is `e2e-version-delta`, which is not a lane row: it re-runs the build's last step (`verify_versions.py`) against the installed binaries, with `--out` and `--home` on a tmpfs `/tmp` because the container runs as uid 10001 and `/opt/mllm/lock` is read-only to it.

The image tags are values, never rule targets: `mllm-e2e:local` contains a colon, which make would read as a target/prerequisite separator. Neither tag has a registry component, so a bare `docker push` fails by construction, and `docker save` of a host-lane container is equivalent to exporting a credential.

The whole-lane wall-clock cap (`MLLM_E2E_MATRIX_TIMEOUT_S`, default 3600) is exported rather than passed per target, and enforced in the host-side driver (`MatrixBudget` in `tests/container/harness.py`, claimed by `run_row` before every `docker run`): once it is spent the driver starts nothing further, names which rows ran, failed and never started, and exits non-zero. The per-row cap is per CLI and lives in `redirect.yaml` next to its measurement.

## Container lanes and spend guards

**Each `-m` expression is a spend guard, not tidiness.** Every tier the lane can bill for carries its own marker, and the cheaper tiers exclude it by name, because a recipe inherits the caller's environment and a developer who happens to export `OPENROUTER_API_KEY` must not spend credit on a gate whose contract is "no key, no network, nothing on the host".

- `e2e-container` selects `container and not live and not live_provider`. The credentialed provider lane's tests carry `container` and `live_provider` and deliberately not `live`, so `container and not live` alone would select them.
- `e2e-container-host` adds `not live_native_phase and not live_next_command`. The claude-code per-phase rows are native Task dispatches: every turn is real spend that never crosses `/opt/mllm/bin` and never appears in the row's `num_turns`. Measured at about 0.60 USD per write row against 0.0080 to 0.0094 USD for an executor host's equivalent, they would make the cheap tier 3 to 5 USD more expensive per pass, so they have their own target.
- The OpenRouter key is not demanded by `e2e-container-host` since 2026-10-02: codex and claude-code rows run on the developer's own subscription when its credential file is present (`harness.default_host_creds`), so a subscription-only run needs no key and its opencode rows skip into the census as named skips. The lane itself refuses a run where no row could execute (`_refuse_empty_lane`), so dropping the gate cannot turn "nothing ran" green. `MLLM_E2E_HOST_CREDS=openrouter` forces every row back onto the key.
- **`e2e-container-host-phases`** is a separate target for two independent reasons. Cost: `MLLM_E2E_BUDGET_USD` defaults to 2.00 and is the lane total (`_Spend.check()` refuses to start a row once the running key-usage total reaches it, and since 2026-09-23 the mid-row poller in `tests/container/host_spend.py` also stops the row that crosses it, or its own `cost_budget_usd × MLLM_E2E_ROW_BUDGET_HEADROOM`, as `budget-exceeded`); a tier of 3 to 5 USD crosses that inside its third row, leaving a half-covered tier, so the target defaults to 6.00. Raise the dedicated key's own spend limit above that figure before first use. Wall clock: native phase rows measured 80 to 376 s each and the existing rows already spend 1968 s of the 3600 s cap, so a combined lane would exceed it. Raise either bound on a recorded overrun, not pre-emptively.
- **`e2e-container-host-next-command`** runs one `generate-tasks` row per host and route the lane can run, each with a short typed follow-up session that hands the printed command to a fresh session. Measured 2026-10-01 at 0.001 to 0.03 USD a row on deepseek v4 flash and about 0.13 USD for claude-code on gpt-6-luna: cheap but paid, so it is its own tier. One row at a time is this expression plus `-k '[<row id>]'` (brackets included).
- **`e2e-container-host-discovery`** and **`e2e-container-host-invocation`** are the free host tiers: no credential, no route out, `--network none`. Discovery stages the shim, crosses the reload boundary and asserts the command is listed and invocable. Invocation types the exact `/multi-llm …` string the README and `docs/hosts.md` publish into a fresh session whose model is the loopback stub; what is under test is argument delivery, answered by the bytes the host sends, so the stub is no compromise. Their modules carry `container` alone (selecting `live` would hide them behind the gate that makes the credentialed rows unrunnable), and invocation also runs under `make e2e-container` on purpose, so a documentation claim that has gone false surfaces on the gate a contributor already runs.
- **`e2e-live-provider`** is the credentialed provider lane. It is not a tier of any other target, because the provider lane under `e2e-container` runs `--network none` against the stub and the host lane's PATH wrapper scrubs every vendor credential from providers. Three properties are contract: it is a prerequisite of nothing (`tests/test_makefile_lanes.py` parses the Makefile to assert that no goal reaches it, since a credit-spending target reachable from another goal is a bill nobody typed); the `live_provider` marker, not the recipe, keeps it out of CI; and it never builds the image (`e2e-image` is deliberately not a prerequisite, so a stale image is a visible failure instead of credits spent on the wrong binary). The key is read host-side from `~/.config/multi-llm/e2e.env` (0600, outside git), reaches the container only as `-e OPENROUTER_API_KEY`, and the run record redacts it from the CLI's stdout before anything is written. `CLI=<id>` passes `-k '[<id>]'`: the brackets select the parametrize id, because a bare `-k pi` also matches the `skipif` marker keyword every item carries (`ski-pi-f`) and silently ran the whole ten-row lane (measured 2026-08-19).

## The unpinned image and credentials

**The `@latest` image installs every CLI unpinned, so its targets never touch a credential by default.** Running the same suite under that image on a machine that exports `OPENROUTER_API_KEY` would select the host lane too and hand unreviewed third-party binaries a live key and outbound network. The lane is therefore selected explicitly and no credential variable is passed into pytest.

- **`e2e-container-latest`** is credential-free by construction. It unsets the vendor keys, runs `container and not live and not live_provider` with `-rs`, and prints the version delta first. `-rs` matters: the surface probe reports a changed help digest as a skip, and without it pytest swallows the `DRIFT REPORT — …` reason lines. The durable half of the report is written per row to `skills/multi-llm/tests/container/runs/<utc>/cli-surface-drift.json`. There is no aggregating `--drift-report` pytest flag: the recipe once ended in one, no `pytest_addoption` registered it, and pytest exited on `unrecognized arguments` after the full image build having reported nothing.
- **`e2e-container-latest-host`** is the one place an unpinned image is allowed near a key, and the guard is a target-level refusal, not a README sentence. Both checks are `lane_guard.py` subcommands, so `tests/test_makefile_lanes.py` executes them; any exit but 0 stops the recipe. The key is required up front: a keyless run used to skip the opt-in guard, build the whole image, skip every row and exit 0, which is the `not-run` outcome the design forbids, and refusing first means a missing key costs no image. The zero-executed-row guard runs after pytest (`--allow-empty-host-lane` is deliberately not mirrored here): a host-lane row that really ran writes `records/<utc>-<row>.json` from `harness.run_row`, so "no record newer than the stamp" is "no row executed". The vendor keys are scrubbed, not refused: `harness.build_run_argv` forwards one explicit `-e` list per row (`OPENROUTER_API_KEY` by name, `ANTHROPIC_API_KEY=` as the literal empty string, nothing else), so a vendor key in the developer's shell never reaches a container and refusing on one would only make the target unrunnable. The scrub is host-side only: the empty `ANTHROPIC_API_KEY` still arrives in the container, the one spelling that keeps Claude Code off the developer's own Anthropic subscription. Unsetting `OPENROUTER_API_KEY` would instead delete the lane's credential, since `-e VAR` forwards nothing when the variable is unset. The version delta prints before the first row because the list of pins that moved is what the opt-in accepts (it was once spelled `--print-version-delta` at pytest, which nothing registers).

## Pin updates and housekeeping

**`e2e-lock-update` moves what the `@latest` image proves, and names the rest.** The evidence is what a real `MLLM_PIN_MODE=latest` build carries: its version census (`/opt/mllm/lock/cli-versions.installed.json`), the `package-lock.json` that `npm install @latest` resolved and, for rows installed as a plain file, the artifact bytes. `lock_update.py` rewrites the npm layer and the `install: download` rows from those and refuses, by name and with the command, the rows it cannot substantiate (`goose`, whose tarball the image unpacks and discards, and `aider`, whose pin is a `--generate-hashes` requirements file). The image-level pins (base digest, platform, uv) are held by the latest build on purpose and change by hand. The rewrite is verified by rebuilding the pinned image: `npm ci` against the new lockfile, each artifact's sha256 checked before it runs, and `verify_versions.py` with the CLI rows enforced; `lock_update.py verify` then grades the record against that census. A failure after the write prints the exact `git checkout --` that reverts it. `cli-surface.yaml` is deliberately not rewritten: it is a contract, not a pin, and a changed help digest is a deprecation notice to read, so the re-seed command is printed instead. The recipe once passed a `--lock-update` flag to pytest that nothing registers, collected the whole suite and rewrote nothing.

**`runs/` is the raw evidence bundle: ephemeral, gitignored, safe to delete.** Gitignored is not absent, though: anything that copies a working tree ignores `.gitignore` (`codex plugin add` from a local-path marketplace takes the directory as it stands), so an uncapped `runs/` is a distribution problem as well as a disk one; it reached 1.5 GB against 18 MB of tracked files. The lane prunes itself on every row (`harness.prune_runs`, `MLLM_E2E_RUNS_KEEP`); `e2e-prune` is the same sweep on demand and `e2e-clean` removes every bundle. `records/` is untouched by both and local-only apart from the schema and the codex release network-check records.

`opencode-stage` stages the OpenCode plugin payload for the image's COPY. It is staging only (no `npm pack`, no secret sweep, no stamp) so that building a test image can never look like a step toward publishing one, and it is a prerequisite of the image targets because `dist/` and `skills/` under the package are gitignored build output that a fresh clone lacks. It passes `--allow-dirty` by default (`OPENCODE_STAGE_DIRTY`), because a test image must match the working tree it is built from. The full gate overrides that: row 8 grades the package inside the image, an image staged from a dirty tree is not the candidate, and a clean `git status` cannot see ignored files, so the gate also reads the payload digest back out of the image id (`release_gate.py image`). `MULTI_LLM_ALLOW_DIRTY` is blanked on that line so the exported opt-in cannot re-enable what the flag left off.

## The OpenCode package gate

**Build and pack are separate, and every recipe runs the build explicitly.** `packaging/opencode/build.py` stages deterministic artifacts and never invokes npm; packing and publishing are owned by the Makefile, so exactly one place each happens and a build cannot quietly produce a second tarball nobody publishes. The tarball secret sweep is a function `build.py` exposes, called after `npm pack` because what npm writes is what ships and a `prepack` hook runs too early to see a tarball. The manifest's `prepack` hook is only a backstop for a hand-typed `npm pack` and does not fire under `--ignore-scripts`; `test_package_is_built_before_every_pack` asserts the ordering.

**The registry is written once.** `OPENCODE_REGISTRY` is read by `packaging/opencode/registry.py`, and every place npm is consulted on the release path (the `npm whoami` check, row 9's absence probe, the registry-install probe, both publish paths and the post-publish integrity read) passes it explicitly; the workflow reads it from `make -s opencode-print-registry`. npm's registry is configurable (a user `.npmrc`, `npm_config_registry`, a scoped registry), so an inherited setting could otherwise make a gate accept `E404` from a different server than the one publication targets.

**`ALLOW_DIRTY=1` is a named opt-in, never a fallback.** A build that ships local state is one nobody can reproduce, and npm makes a published version permanent. The opt-in is exported as `MULTI_LLM_ALLOW_DIRTY` rather than passed as a flag because `npm pack` invokes the manifest's `prepack` hook with its own fixed command line. `OPENCODE_BUILD_CLEAN` blanks every spelling of the opt-in and uses `env` so it also works as the argv of a gate step, which runs without a shell; every build the full gate runs goes through it, and `--write-stamp` refuses unless every row passed over those bytes. `opencode-publish` builds nothing (see below). In the full gate `ALLOW_DIRTY=1` is a rehearsal: every row may run from a dirty tree, the session says so, and `--write-stamp` and `export-record` both refuse it by name.

**`OPENCODE_TARBALL` names the exact file** (`<name>-<version>.tgz`, from the manifest), never `ls -t | head -1`: a stale tarball of another version beside it must not be the one that is scanned, loaded by row 7 and bound by the stamp.

**`PLAIN_ROWS`** chooses which plain rows the three `-ci` tiers run. `all` (the default, and what the publish workflows and the full gates use) runs each route's whole plain selection beside its `package` rows, so a tier graded by itself stands on its own evidence. `graded` is the PR `package` job's spelling: that job shares a workflow with the Ubuntu `test` leg, which already ran every plain row, so it keeps only the rows a grader reads (opencode's rows 1 to 6 and 5b, `release_gate.py ci-nodes`). The `package`-marked rows, the clean rebuilds and the moved-tree rule run in both. Any other value is refused by name.

**`opencode-package-check-ci`** runs rows 1 to 6 and 5b, which need no Docker, no registry and no `opencode` binary. It writes no stamp, so a CI-tier run can never authorize a publish. It is graded row by row, not by exit code: both pytest selections write junit XML and `release_gate.py grade-ci` reads it against the node ids each row declares, so a skip, a deselection (the test is simply absent) and an empty selection each fail the row by name where pytest would exit 0 or 5. Both selections always run and the grader always reads both, so a red run still names every row it cost.

**`opencode-package-check` stamps only what it ran, in this run.** The stamp is what the release rests on and npm makes a version permanent, so a stamp written after a subset of the rows is an authorization nobody earned. Recipe order does not enforce that: `begin` opens a gate session (earlier evidence deleted, a fresh id beside the candidate commit), every row's grader writes its evidence under that id, and `--write-stamp` refuses unless every row passed in this session over these bytes, this commit, the pinned host and the gated tarball. A zero pytest exit never satisfies a row. The steps are serial recipe lines, never prerequisites, so `make -j` cannot reorder the reset after a row, build the image before the candidate or race row 8 against a rebuild; each runs through `release_gate.py step` under a wall-clock bound and keeps its output in `$(OPENCODE_GATE_DIR)/logs/<step>.log`.

- Row 7 installs the pinned OpenCode from the container lockfile under a scratch prefix (`bump.py install`), loads the gated tarball extracted as a directory in an isolated home and runs init and status through the real tool in a committed and a no-commit project (`probe.py row7`); `record 7` re-reads what the probe says it did.
- Row 8 runs on the image the gate builds itself, staged from the clean candidate under its own tag (`mllm-e2e:opencode-gate`; `mllm-e2e:local` is whatever the last `make e2e-image` staged, dirty tree included). `image` resolves it to its immutable id, reads the payload digest out of that id and refuses one built from other bytes, and refuses an inherited `MLLM_E2E_IMAGE` that names another image before row 8 runs. The scenario module runs with every provider key unset and `MLLM_E2E_RUNS_KEEP=0` (so the lane cannot prune the bundles `check-row8` is about to verify); `check-row8` refuses a scenario missing, skipped, ungraded or failing, a record from another image or run, and a bundle `make e2e-verify-record` does not match.
- Row 9 is the shared entry point `opencode-registry-absent` (Node built-ins only), decided on npm's error code: only `E404` is absence, exit 0 is "already published" and anything else is an unknown. The publishing workflow's jobs run the same script: the two tiers still run separately, but they share one implementation rather than two hand-kept copies.

**The stamp never travels.** It is gitignored and never uploaded, because a stamp from another machine attests to that machine's rows. CI consumes no stamps: its jobs re-run rows 1 to 7 and 9, and row 8, which needs a Docker daemon the runners lack, reaches CI only as the release-gate record exported at the end from the session that authorized the stamp, into the gitignored `$(OPENCODE_GATE_DIR)/export/` (never `records/`, where an untracked file would make the tree dirty and the stamp refuse). It is then copied into `skills/multi-llm/tests/container/records/` and committed in the default branch's own commit after the fast-forward, never in the tag's tree.

**`opencode-registry-absent`** reads `OPENCODE_REGISTRY` and refuses any other `--registry`. `OUT=<file>` keeps the row-9 evidence JSON. `PACKAGE_JSON=<file>` asks about another manifest (the workflow's canary `opencode-multi-llm@0.0.0`, which must answer `E404`) and is honoured only from the make command line: an exported one would quietly point row 9 at a different version, so one from anywhere else is refused by name.

**`opencode-publish` is no longer a publish path.** It used to upload from the package directory with `--provenance`, and that shipped the wrong bytes: the `prepack` hook rebuilt `dist/` there and npm uploaded the rebuild, while `--check-stamp` had compared a separate rebuild a moment earlier. The guarded path uploads the exact tarball its gate packed, scanned and loaded (`npm pack` once, then the file, with `--ignore-scripts`); a tarball upload runs no lifecycle scripts, so nothing can repack it. The first release (0.1.1) was a one-off laptop upload; [Host integration](hosts.md) says where its record lives.

**The supported OpenCode is its newest release, and only that one.** It is the adapter's `min_version` and `verified_version` at once, and `engines.opencode`, the package README, the container's `opencode-ai` pin, lockfile and `cli-versions.lock` row and the mock's `--version` all name it; `tests/test_opencode_version_pins.py` fails on any one that does not. `opencode-bump` is the one way to move them: it re-captures the fixtures offline from a localhost stub at no cost and rewrites every pin, writing nothing before its npm steps succeed. `opencode-latest-check` exits 1 when npm's latest `opencode-ai` is newer than the pin; it is a make target, not a scheduled workflow, like the container lane's drift probes.

**`opencode-check-bump` is the shared-version check** (Codex's `--check-bump` runs the same one). The version is `pyproject.toml`'s, shared by all three distributions, so HEAD's version must either be released already with this same shared payload, or be newer than every `claude-v*`, `codex-v*` and `opencode-v*` tag and every version npm lists for the package (npm's own `0.0.0-stage` stub, `"stub": true`, is reported and skipped). It reads git and the registry, writes nothing, and refuses a shallow or tagless clone rather than reading it as "no releases". It is deliberately in no `tests` workflow leg and not in `opencode-package-check-ci`: after V is released, `master` may change shipped bytes while still saying V, and the check refuses a release from that state but must not turn `master` red over the legal edit. The exception is `claude-check-release`, a separate rule over the Claude tree that does run on pull requests.

**`opencode-registry-check`** is the registry-install probe: what npm serves for `SPEC`, installed by the pinned OpenCode from the single registry into a fresh home, compared with the candidate rebuilt from `TAG`'s commit before the first tool call, then driven through `multi_llm` (`packaging/opencode/registry_check.py`). `ENVIRONMENT=ci-runner` writes the bootstrap record (seven criteria), retired after `opencode-v0.1.1`; it covers a first release only, so every later tag refuses it. `container` drives a stock container from this host and adds the warm-offline run on its committed image with `--network none`; `vm` runs here and waits for the VM's interface to be detached. `REHEARSAL_REGISTRY=http://127.0.0.1:<port>` (a `registry_stub.py serve` of the gated tarball) makes the run a rehearsal whose record is never release evidence, and is honoured only from the make command line, because an export left over from a rehearsal would turn step 5's real run into another rehearsal. `--frozen --no-dev` because the probe needs only the runtime lock.

## The Codex and Claude Code plugin trees

Both generated trees (`packaging/codex/multi-llm/`, `packaging/claude/multi-llm/`) are committed, so the Git marketplace route serves the checked-in copy with no build on the user's machine and there is no pack and no upload: `codex-publish` ends at a tag push, and publication proper is the promote job in `.github/workflows/publish-codex-plugin.yml` fast-forwarding `release`. Each has two builds, and which runs is the ordering constraint:

- `*-regen` is the development regeneration: `--allow-dirty`, writes the tracked tree, takes no stamp, reaches no publish, and runs before the commit so the source edit and the output it implies land in one commit.
- `*-package` is the clean build after the commit: it refuses dirty inputs whatever `ALLOW_DIRTY` says (`MULTI_LLM_ALLOW_DIRTY=` on the recipe line, because the variable is exported whenever `ALLOW_DIRTY` is set and no spelling of the opt-in may reach this build), and the rebuilt tree must equal the committed one. Both check targets and `codex-publish` stand on it.

The codex and Claude route test lists (`CODEX_PACKAGE_PYTEST`, `CLAUDE_PACKAGE_PYTEST`) are their own, not the OpenCode `PACKAGE_PYTEST`, which names the OpenCode suite literally. `test_uv_candidates.py` is registry-neutral (it greps the whole tracked tree), so it sees a candidate-list reader added anywhere under `packaging/`. `PACKAGE_PYTEST` names its files rather than appending to `$(PYTEST)`, which already names the whole tests directory and would collect the entire suite twice in a job that exists to grade a tarball.

**`codex-package-check` stamps only what it ran.** The CI tier, then the container rows on three codex builds (the container's pin, the plugin's declared minimum `hosts.codex.package.min_host_version`, and npm's newest resolved now, row 14), then bump discipline, then the stamp. Every tier ends in `release_gate.py check`, which reads the run records this invocation wrote and refuses unless each row the tier requires came back graded `pass` on that image, that codex and an installed tree carrying this checkout's digest; `--write-stamp` refuses without all three tiers' evidence over these bytes. pytest's exit code alone is not that, since a module skipped for want of a daemon exits 0. The tiers are serial recipe lines for the same reason as the OpenCode gate, `codex-gate-reset` begins a gate session so the stamp takes only this invocation's evidence, and each tier's image build and container rows are `step`s bounded by wall clock, so a hung build or row ends the gate. Under the minimum tier the lane holds rows to `min_host_version` instead of `host_matrix.yaml`'s `plugin_floor` (which tracks the pin and would refuse them). The ceiling tier asks npm now and a failed fetch stops the gate naming what it could not reach, never a skip. `codex-gate-derived` is internal: it builds the pinned image with only codex moved (`Dockerfile.codex-version`, built with no context, the fetch being that build's one network access) and runs the tier's rows on it. `codex-publish` is developer-facing and never CI, since CI holds no credential that pushes a tag; it refuses on a missing or stale stamp and on a digest that moved since the newest `codex-v*` tag under an unmoved version.

`claude-check-release` is the moved-tree rule, reading git only. `CLAUDE_RELEASE_BASE` is the ref to compare with besides the newest `claude-v*` tag (a pull request's target, or on a push the commit master was at before it); a branch name can hold make and shell syntax, so `$(value …)` keeps make from expanding it and the shell reads it from the environment, never from the recipe's text. `claude-check-bump` adds the shared-version history check over every family's tags and npm. `claude-package-container` shows the plugin as a user gets it, in the image: the sparse Git registration, the install, a fresh session's own account of what it loaded, the hooks really running, the published `/multi-llm:multi-llm` string, the dispatcher from the cache copy and the documented update. No key, no route out, no cost: the host's model is the loopback stub, so it answers "does it load and run" and leaves "does a model follow it" to the credentialed `claude-code-package-*` rows. Run it before a release, after `make claude-package-check-ci`; it also runs under `make e2e-container`.

## Release helpers

[`packaging/claude/README.md`](../../packaging/claude/README.md), "Release procedure", is the procedure. `bump-version` moves the version all three distributions share (the owner `skills/multi-llm/pyproject.toml`, every hand-kept mirror, then the capability docs and both generated trees); it plans every edit before writing any, refuses a mirror that does not already say the current version and commits nothing. It is not `opencode-bump`, which moves the OpenCode CLI pins. `claude-hook-install` writes `.git/hooks/pre-push` (local, never committed): a push of `master` then has to pass the moved-tree rule against the remote's master and a clean rebuild of both generated trees from the pushed commit, and a `claude-v*` tag has to name its commit's version on a commit the remote's master has. `master` has no branch protection and CI reports only after a push lands, so this is the check that runs before users can fetch anything. `claude-publish` runs those checks plus the shared-version history check (it fetches and reads the registry) on the local `master` and prints the push and tag it would make; `PUSH=1` then pushes `master` as a fast-forward and the `claude-v<version>` tag. It never forces and does not run the Docker install check: run `make claude-package-container` first.

`refresh-model-catalogs` is run by a person who is logged in, never in CI: most listings need a login or the network, and the script refuses when `CI` is set. It rewrites `tests/fixtures/model_catalogs/<source>.json` for each source (`SOURCES` limits the run); review the diff before committing.
