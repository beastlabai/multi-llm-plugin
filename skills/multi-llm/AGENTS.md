# Multi-LLM Skill — Development Guide

## Architecture

- Orchestrators produce JSON instructions for Claude Code to execute — they never modify code directly
- **`multi_llm.py` is the single entrypoint.** Every mode is `uv run --project <skill-dir> -- python <skill-dir>/multi_llm.py <mode> [<positional>…] [--host <id>] [mode flags…]`, so a host shim resolves one path once and routes nothing itself. `<mode>` is a bare word and must be `argv[1]`; unknown/missing is exit 3 listing the valid modes. Positionals are normalized into the flags the target already parses (plan modes `<plan>`→`--plan-file`; `ask` `<plan> <question>`→`--plan-file` + `--question`, falling back to a dispatcher-written `--question-file` past `MAX_ARGV_QUESTION_CHARS`); an extra positional is exit 3. Everything after the positionals is forwarded **verbatim as a Python list** to that mode's `main(argv) -> int`, imported lazily and called **in-process — never `subprocess`** (one `uv` resolution per invocation, a plan path with a space survives by construction, `shlex` never runs on this path). `multi_llm.py <mode> --help` prints the target parser's help. Exit codes are uniform and never remapped: `0` done, `1` unexpected error, `2` nothing to do / phase already complete, `3` needs a human. **What a phase *found* is never an exit code** — findings are artifacts and bracketed stdout markers, so a review that completed is `0` however serious its findings are. `review-code` used to return `1` when it found HIGH-importance issues, which claimed an error that never happened: it stopped `full` at `review-code`, one phase before `apply-code-fixes` (the phase that fixes what the review just found), and put `state: "error"` on the result line of a successful run. It now prints `[HIGH_PRIORITY_ISSUES] <n>` and returns `0`; `--fail-on-high` is the opt-in for a standalone CI gate and is exit `3`, never `1`. Every invocation ends with exactly one machine-readable stdout line, `MULTI_LLM_RESULT: {"mode","phase","state","exit","artifacts":[…],"next":…}`, emitted even on a crash (`next` is `null` when no follow-up is owed). **Optional** keys join them. `consolidation_recommended` (`{valid_groups, threshold, command}`), present only on a review phase that crossed `CONSOLIDATION_RECOMMENDED_THRESHOLD` — written to `{phase}/.status.json` at the same site, carried through `detach.classify_run` and re-emitted (with one rendered line) by `status --view run`, because the `[CONSOLIDATION_RECOMMENDED]` marker is a bare `print` and a detached caller never reads the log: measured 2026-09-16, a 29-group run printed the marker and the session model told the user no consolidation had been recommended. Deliberately **not** `next` — `--consolidate` is one of the dispatcher's `mechanical_continuations`, which the opencode plugin auto-follows without asking, and following a recommendation would run a phase nobody requested. Two more ride that line on the poll path, both recorded by `status` when the caller named exactly one run (one view plus `--phase`/`--question`/`--run-id`): `progress` — the watched run's own `.status.json` `progress` object, carried through **whole and unreworded** (a test pins that no key is added to it) — and **`progress_lines`**, its sibling: the same run *already rendered*, an array of opaque human-readable strings a host may print verbatim. In order, each present only when it applies: the fan-out roster, the current-state line (the ticker's `[PROGRESS]` while a slot is live, the human view's `progress:` once every slot is terminal) and `just finished:` (what crossed into terminal during this call's own `--wait`). `detach.launch` records the roster line the same way, so a `--detach`ed fan-out names its models on the first result line a supervising host can read rather than a poll later. Opaque strings rather than named fields on purpose — the consumer's rule stays pure identity, "show every supplied line I have not shown", and cannot grow an opinion about which line is which — and a sibling rather than a key inside `progress`, which stays what the status file wrote. It exists for the OpenCode **package** route, the one route with no agent in its poll loop (`src/index.mjs`'s `execute` supervises the run itself and the model makes one blocking tool call), and that file composes no sentence of its own: the wording is composed in Python by the renderers that already own it and relayed verbatim. Empty entries are dropped, so an invocation with nothing to show grows no key. `answer_origins` (`{answered, file, stdout, fallback, accepted, unrecorded, kept, warn_all_fallback}`) is ask's: present on every ask run that reaches its closing report (all zeros and `false` on a zero-answer run) and on no other mode, written to the question dir's `.status.json` in the same `update_status` call as `state`, carried by `detach`'s run view and re-recorded for a pinned `status --view run` — the route `validation_counts` takes. Its integers are the `answered: …` counts line's, read from each answer's `origin_<model>.txt` record, and `warn_all_fallback` is the `[WARN]`'s own predicate (every file-capable answer was recovered from stdout), so a host that reads only the result line sees the condition; it never moves `state` or the exit (plans/ask-answer-recovery-and-false-success.md D7.2). **`user_next_step`** is the workflow's next phase as the command the *user* types (plans/next-phase-command.md): `{"phase", "command", "optional_before": [{"phase", "command", "why"}], "complete": false}` (`optional_before` omitted when empty, and every rendering puts the primary first; since fix round 16 it also carries `manual_tasks`/`manual_tasks_note`, as below, whenever implement deferred tasks the user still owes — Codex racing run 6's 06r/07 named T009 from the notice but never its closing command — and `modes.TOOL_USER_NEXT_STEP_LINE` and every route's relay rule say to give them on any result; every block renders them, after a command block's commands too — fix round 17), or `{"phase": null, "command": null, "complete": true}` once no required phase is left (every answer ends with `markdown` since fix round 22: the step as the report's closing section, each command fenced alone, which the tool and file routes copy as it is — `next_phase.render_next_step_markdown`; `manual_tasks_note` is then the sentence leading into `manual_tasks_command`, printed natively as `[MANUAL_TASK_COMMAND]`, which the Stop hook holds the report to) (plus `manual_tasks: [{id, title}]` when implement deferred tasks the user still owes — a task skipped because it depends on one also carries `waits_on`, that manual task, and its `[MANUAL_TASK]` line and `status`'s trailer say implement runs it once that one is recorded done (`next_phase.waits_on_note`, `StateManager.deferral_root`, fix round 17) — and beside it `manual_tasks_note`, the one line saying how to record them done — `--implement <plan> --resume --human-task <id>=done` in the host's spelling, printed as `[MANUAL_TASK_NOTE]` and on `status`'s manual-tasks line, fix round 14; such a `done` completes a manual task under every strategy, and a resume that dispatches nothing keeps implement's completion date on both legs — read from `state.json`'s `skipped` statuses and the `task_titles` implement records, never from tasks.md, scoped to the decomposition implement ran last (`implement_task_ids`) and to deferrals — a pause-and-ask "Skip" and its dependents are not owed; additive, 2026-10-05; the native leg's emit writes those statuses itself through the executor's own `write_batch_scheduler.persist_human_task_plan`, and a manual task of a completed implement with no answer on record at all is owed too, via `implement_human_task_ids` — fix round 7) — a complete workflow is an answer, so the key is present then and **absent always means "no answer"** (not a workflow phase, the gate found the phase unfinished, a failed run, or an excluded invocation), never "complete". One builder, `utils/next_phase.next_phase_commands`, makes it from `get_workflow_status`'s `phases` map and the host's `next_command` template; the command is the mode flag, the plan path exactly as its source supplied it and, only when that phase is recorded `in_progress`, `--resume` — never `--models`/`--quick`/`--yes`. `multi_llm.main` sets it for a workflow-phase mode on exit `0` or `2` (a re-run of a finished phase is the caller who most needs it) and for `full` on exit `0`, only when the finished phase is on record (completed, skipped, or `in_progress`: exit 0 at a `[…_PENDING]` marker or the native first call of an apply phase is not a finished phase), never beside a non-null `next` (which is what excludes a real `--detach` launch or `--if-not-running` re-attach: `detach.launch` records the run's poll command as `next`), never on `1`/`3`, never for a write-phase invocation without `--exec-subagents` (it hands its batch loop to the invoker and records the phase `in_progress` at emit time — `StateManager.mark_phase_started`, since 2026-10-05; the builder would answer `--resume` for the phase being run), except the apply phases' closing `--mark-completed` call, which records the phase completed and carries the key like any finished phase (2026-10-05); implement's closing step is `util finalize-tracking --mark-completed`, a util that carries none, so that leg's answer comes from the report step's `util next-command` (2026-10-01: there is no `--detach` test, so a `--detach` invocation that launches nothing — the completed-phase guard's exit 2, which returns before `maybe_detach` and which the tool routes hit on every re-run because they always append `--detach` — carries the key like any foreground exit). A builder failure omits the key and the block, prints one stderr line and never moves the exit code. Deliberately **not** `next`, for the reason `consolidation_recommended` is not: a tool route auto-follows `next`, and following this would start a paid phase nobody asked for. Beside the key, the emitter prints the `[NEXT_COMMAND]` block (below) above the result line — on stderr when the invocation asked for JSON output (`--output-format json`, `status --json`).
- **`modes.py` is the one owner of the mode table** — mode words, the closed alias table (`review`→`review-plan`, `code-review`→`review-code`, `tasks`→`generate-tasks`; no prefix or fuzzy matching), positionals, lazy dispatch targets, phase names, core instruction files, and which modes are user-facing. `SKILL.md`'s `argument-hint`, `multi_llm.py --help` and `check_workflow_prerequisites.py`'s `--mode`/`--phase` choices are all **rendered** from it; adding a mode is a row, and `tests/test_instruction_portability.py` fails if the dispatcher and `argument-hint` disagree. Note the one place mode word ≠ phase name: mode `review-code`, phase `code-review`.
- **`utils/cli_common.py`** owns the cross-cutting argparse **parent** (`--host`, `--yes`/`-y`/`--non-interactive`, `--interactive`/`-i`, `--detach`, `--if-not-running`, `--max-detached N`, `--exec-subagents`, `--skip-prerequisites`, plus the suppressed `--internal-worker`/`--internal-run-id` re-entry flags), included by every `*_orchestrator.py` parser plus `check_workflow_prerequisites.py` and `init_config.py`, so a direct invocation accepts the same flags with the same semantics. It also owns skill-dir resolution — `os.path.abspath`, **symlinks preserved, never `realpath`** (`link-skill.sh` symlinks the plugin cache at a dev checkout; resolving would move `uv run --project` off the `pyproject.toml` the host loaded) — plus the printed-command builders, the `MULTI_LLM_RESULT` emitter and the per-invocation record (mode word + normalized argv) a detached child re-executes. It also owns `--dry-run-subagents` (D3l: render every command, start no child). `--exec-subagents` is implemented for the read/analyze phases **and** the four write phases (below); `--detach` covers every long-running mode (below).
- **`--detach` self-daemonizes every long-running mode**: the fan-out modes (`review-plan`, `review-tasks`, `review-code`, `ask`) plus the executor-backed write modes (`apply-suggestions`, `apply-task-suggestions`, `apply-code-fixes`, `implement`) plus `generate-tasks` and `full`, whose orchestrators landed with the Phase-3 sequencing — so the plumbing they registered for is now the plumbing that runs (`generate-tasks` claims `{plan}/generate-tasks/`, `full` claims `{plan}/full/`)). Everything else exits 3 rather than accepting a flag that does nothing. The write phases cross the **same** boundary through `apply_orchestrator_base.maybe_detach_write_phase` / `implement_orchestrator.run_implement_write_phase`, placed after all pre-flight and before the first child, so one spawn implementation and one `.status.json` claim serve both halves; per-task write progress lands under `progress.write_subagents`. One boundary crossing, `utils/review_orchestrator_base.maybe_detach`, sits *after* all pre-flight (flags, inputs, model resolution, phase-dir creation, lock pre-check) and *before* any model or agent CLI runs, so a bad flag or an unconfigured provider fails on the caller's terminal with **no child and no log**. The `--reaggregate` branch of every review orchestrator crosses the same boundary, after its one pre-flight (the phase dir exists): measured 2026-09-14 on review-tasks, that branch ran ahead of the boundary, the re-dispatch of the failed validation batches finished in the invoker's foreground with no run banner, and the opencode plugin — which composes `--detach` on every launch and adopts a run only from the banner — reported the completed run as "the launch reported no run_id on its banner". The invoker forks (POSIX: `setsid` + a second fork, so the worker reparents to init and the invoker has no child to reap; Windows: `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`), waits ≤10 s for the worker to publish its own identity, then prints the log path plus the `status`/`--abort` commands. **`{phase}/orchestrator-run.log` is handed in as the worker's stdout/stderr on both platforms, so it holds the whole worker and not just the part after the boundary** — `process_control.spawn_detached` opens it append-only and dup2s it onto the child's fds 1/2 in the intermediate, and `enter_detached_worker` (which `maybe_detach` reaches only at the *end* of pre-flight) compares `(st_dev, st_ino)` and reopens nothing. Until 2026-09-16 the POSIX leg gave the worker `/dev/null` and the worker reopened the log itself, so every setup line an orchestrator prints on its way to the boundary went on the floor: a completed `apply-suggestions` log opened at `[DETACHED_RUN]` with no `Loaded 33 suggestion groups` and no `No user preferences detected` — the notice under which it applied all 29 items — and `review-plan`'s log had no `Loaded plan:`/`Backup saved:`/`Models:`. The invoker's own copy still goes to the caller's terminal, which is the pre-flight rule; the setup lines therefore sit *above* the `[DETACHED_RUN]` banner in the log, and a worker that dies before the handshake now leaves its reason in the file the launcher's failure message tails. The child re-executes `uv run --project <skill-dir> -- python <skill-dir>/multi_llm.py <mode> … --internal-worker` — **never bare `python`** (`sys.executable` inside `uv run` loses the lockfile and `--project`) — with `--detach`'s implications (`--yes`) written out and paths absolute. `--detach` implies `--yes` and is exit 3 with `--interactive` at parse time. Never combine it with a host's own background primitive: Claude Code uses `run_in_background` and never passes `--detach`. **The next-step block in `orchestrator-run.log`**: a finished worker prints `[NEXT_COMMAND] <command>`, then per `optional_before` entry `[NEXT_COMMAND_OPTIONAL_WHY] <why>` directly above `[NEXT_COMMAND_OPTIONAL] <command>`, or `[WORKFLOW_COMPLETE]` followed by one `[MANUAL_TASK] <id> <title>` line per deferred implement task, above its result line (`next_phase.render_next_phase_lines`, the one renderer); a command line carries the command byte for byte and nothing else, so copying one copies no prose. A launched detached run's `user_next_step` reaches a host on its **terminal poll**, never on the invoker (which owes the poll as `next`). Because `build_worker_argv` rewrites `--plan-file` to an absolute path, the invoker ships the plan argument as it was typed in `MULTI_LLM_PLAN_ARG` (beside `MULTI_LLM_REPLAY_FLAGS`, same reason: the worker's own argv can only carry the rewritten path); `begin_worker_run` pops it and `RunHandle` records it once as the run record's `plan_arg`, next to `plan_file`. The worker's block and the terminal poll print that value, so a relative plan stays relative; a record without it (older, or a hand-started worker) falls back to the absolute `plan_file`. A native leg's continuation has the same gap in the foreground: its `next` (`--reaggregate`, `--reaggregate-consolidation`) is a printed follow-up and names the plan absolutely, so the hand-off writes the plan as typed into the continued phase's `.status.json` as `plan_arg` and the continuation prints that, only while it names the same file from its cwd (`multi_llm._remember_plan_spelling` / `_continued_plan_arg`; racing re-run 4, Claude Code 03, 2026-10-05). Since fix round 14 the native hand-off itself names the plan as typed when that spelling passes the same check (`cli_common.typed_plan_for`: the generate-tasks follow-up, the review and code-review validation hand-offs, consolidation's, the salvage reaggregate), and implement's handoff JSON carries `plan_arg` for the closing `util finalize-tracking --plan-file`. Both files sit in the run's output folder, which every jailed batch can write, so a `plan_arg` read back from either is printed only when `next_phase.recorded_plan_spelling` passes it: `realpath(strict=True)` names the same existing file (non-strict collapsed `plans/$(cmd)/../foo.md` onto `plans/foo.md`) and it holds only `shlex.quote`'s bare characters or a plain space, else the plan as received (fix round 11). A continuation with no passing hand-off spelling falls back to the phase's run record's `plan_arg` under the same check, so the "advance it with: … --reaggregate <absolute plan>" line a detached run's status prints ends with the plan as its launcher typed it (fix round 11).
- **`{phase}/.status.json` is one file with one schema**: today's checkpoint plus two reserved objects, `run` (the process machine `starting → running → {done, failed, aborted}`, heartbeat, pid + `process_start_time` identity, `exit_code`, `error`, `resolutions`) and `progress` (display only). `run` is the detached worker's alone (only `claim_run` writes it); `progress` is written by **every** run, foreground or detached — `detach.report_progress` falls back to `status_file.update_progress` when no handle owns the phase dir, so the invariant is "a foreground `.status.json` gains a `progress` object and still no `run` object", not "gains no new keys". Its reserved keys are `{step, batch_index, batches_total, tasks_done, tasks_total, tasks_generated, failed_task_ids, models, models_done, models_succeeded, models_total, interval_s}` (`status_file.py`'s module docstring is the contract): `models` is the fan-out's per-model map keyed by spec, `models_done` counts *finished* slots and `models_succeeded` the slots that produced a usable result, `interval_s` is the resolved ticker cadence. `run.state` is **not** the top-level `state` (the phase machine resume reads) — a crashed fan-out is both. `progress.models_done` is written by the fan-out that owns the models: the review base advances it to `len(model_specs) - len(failed_models)` beside `models_completed`, and `code_review_orchestrator` does the same at its own `models_complete` write and, since 2026-09-16, via a `slot_finished()` of its own inside `run_all_reviews` (mirroring the base's) — before that fix its fanout step wrote `models_done=0` and nothing advanced it until the last model returned, so a mid-run poll of a finished-in-part run read `models 0/3` beside three completed reviewers. **Progress is reported while it happens, not only at the end of a stretch.** `run_all_models` advances `models_done` per finished *slot* (a failed or skipped slot included — the recomputation at `models_complete` is what turns slots back into successes), `dispatch_subagent_tasks` reports the step its batch is on before it dispatches (`validating`, `revalidating`, `consolidating`, else `dispatching <label>` — `_DISPATCH_STEPS`), and both executor mirrors write per finished task rather than once at the end (`subagent_executor.run_tasks` counts against the batch's full size; `write_batch_scheduler._run_batch` takes its `finished_in_batch` rows under a lock because a disjoint group dispatches on threads — `in_flight` in the same mirror now names the opposite, a dispatch started and not yet classified, F10). Measured 2026-09-16 on a 516 s `review-plan`: 435 s of fan-out reported `models 0/4` and 62 s of validation reported `grouping`, leaving ~5 s of the run with an informative progress line. Primitives live in `utils/status_file.py` (re-exported by `review_orchestrator_base` as `write_status`/`update_status`, so nothing about the write path changed) because `status` must stay sub-second; `run`/`progress` merge key-by-key like `output_files`, a plain `write_status` cannot erase them, and every write after the worker's initial claim is **compare-and-set on `run_id`** so a closed-out run can never resurrect itself. Liveness is the heartbeat (10 s; expired at 60 s = six missed beats); `{phase}/.lock` (`utils/process_control.py`: `flock`/`msvcrt`, held on an open fd) makes one writer per phase dir, and a second run against a live holder is exit 3 naming it. Every run ends in exactly one terminal state with `run.exit_code` recorded — the worker records its own (nothing is its parent after the double spawn), and `status` closes out `failed(heartbeat_timeout)` with `exit_code: null` when the heartbeat expires and the identity probe says the process is gone. The machine's middle word is written too: both sites that materialize `validation_tasks.json` write `state: validation_pending` beside the `validating` progress step, which `status` used to print as `phase state: grouping_complete` / `progress: validating` for the whole validation stretch. **The phase machine's terminal word is `complete`** (2026-09-11): `run_review_orchestration`, `reaggregate_from_existing_files` and `code_review_orchestrator`'s three completion sites write `state: complete` and `progress.step: complete` right after `mark_phase_completed`, so `status` shows a finished run as finished — before that the last checkpoint the fan-out wrote (`grouping_complete`) stayed on disk forever and the status view read a done run as still grouping. No reader gates resume or reaggregate on the exact word; `state.json`'s `phases_completed` remains the record that matters.
- **`utils/unattended.py` owns the unattended contract (D6): fifteen decision *sites*, three dispositions, no questions.** `ROWS` is the closed table — each site keyed by a stable `site_id`, the modes that reach it, the disposition it lands on (**auto-select** / **fail closed** / **explicit flag** — "ask in free text" is not a fourth option) and where it is enforced; `DECISION_FLAGS` is the D5a input contract, one flag per row whose values enumerate exactly what a question would have rendered. **Exit 3 is reserved across every mode for "unattended run cannot proceed"** (missing uv, unmet prerequisite, contradictory or empty decision flag), distinct from the exit-2 phase-already-complete guard, so a host can tell "needs a human" from "already done". `validate_decision_flags(argv)` runs in the dispatcher *before* any parser so `--models ""`, `--human-task <id>=` and an unknown `--force-strategy` are exit **3** at parse time rather than argparse's exit 2; `choices` on each parser is the second layer. `record_resolution(phase_dir, site_id, decision)` prints `[AUTO_RESOLVED] <site>: <decision>` and, under `--detach`, appends to `run.resolutions` via `detach.record_resolution` → `status_file.append_resolution` (a foreground `.status.json` still gains no `run` keys — `detach.record_resolution` keeps its handle guard, unlike `report_progress`; the `[AUTO_RESOLVED]` line is the foreground record). Auto-resolutions are announced only under `--yes`, so with `--yes` unset a run is byte-for-byte what it was. **The apply phases' own two sites (rows 10 and 11) are recorded, not just taken**: both fire *before* `run()` crosses the detach boundary, where no run handle exists yet and `detach.record_resolution` is a silent no-op — so `ApplyOrchestratorBase._record_resolution` prints the marker at the site and `_flush_resolutions` replays the entries into `run.resolutions` immediately past the boundary. One leg prints it: under `--detach` the invoker reaches both sites and then re-executes itself as the worker, which reaches them again, so the marker is skipped on the leg that is about to fork (`_is_detach_invoker`) and kept on the one that writes the record. Row 11 is not taken at all under `--dry-run` — that flag is itself one of the nine that bypass the no-selection confirmation, and the run it describes as "apply all valid items" applies none. Measured 2026-09-16 on a `--yes --exec-subagents` apply-suggestions run: 29 of 33 groups were applied because nobody had selected anything, `.status.json` said `"resolutions": []`, and the row-11 decision left no trace in the log, the payload or the status view. `--yes` also now *implies* `--agent-decide` in every apply phase (`apply_orchestrator_base.apply_unattended_defaults`) and resolves the human-task strategy to `skip-dependents`; it **never** implies `--skip-prerequisites`.
- **Python never sniffs its host (D6b).** No `isatty()`, no `CI=` read, no `--print` detection: interactivity is *requested* (`--interactive`), never detected, so the same argv produces the same phases in a terminal and in a pipe. `utils/interactive.is_tty()` is gone and `resolve_models(..., unattended=True)` never reaches a picker — it returns `defaults.models` or raises `NeedsHuman` (exit 3). `full-workflow.md`'s "no TTY → skip review-tasks" branch is deleted. `tests/test_unattended.py` parses every runtime module's AST (so a *comment* about `isatty` is not a call) and fails any reintroduction; the one allowlisted `isatty` is `utils/metrics.py`'s ANSI-colour gate, which decides how a line looks and never which phases run. `--yes` with `--interactive` is exit 3, never precedence. **`MULTI_LLM_ROUTE` is the one route signal, and it picks only the spelling a printed line uses, never which phases run** — the same test the `isatty` allowlist applies. The tool servers own it: `modes.ROUTE_ENV`/`modes.TOOL_ROUTES` are its name and values, the surface generator writes each host's pair into `dist/cli-surface.json` as `dispatcher.route_env`, and both servers set it on every child they spawn, polls included, so neither server spells the name or the value. `utils/next_phase.resolve_route` is the only reader and validates it: a value outside `TOOL_ROUTES`, or one the resolved host has no `next_command` cell for (`package` under claude-code), is treated as unset with one stderr line. A detached worker started on a tool route records it as `run.route` (`detach.RunHandle`), and a reader whose environment names none (a shell's `status`, `util next-command`) spells that run's commands in that route, its template and the reserved flags it composes (`resolve_route`'s `recorded`, `next_phase.recorded_route`: the pinned run's record, else that phase's or the plan's newest run of the reader's host; another host's record and claude-code ignore it; no record keeps `default`; fix round 24, live run 10: a shell's `status --host codex` printed the file shim's sentence for a run the plugin's tool started). On claude-code it is ignored: the route there is read from the dispatcher's own skill root (`cli_common._SKILL_DIR`, symlinks preserved) — `skill` when it ends in an `install_paths` tail (`.claude/skills/multi-llm`), else the plugin's `default`. A valid value exported by hand beside a file shim of the same host is the accepted residual; it is not a user setting.
- **The prerequisite gates are the one place `--yes` must not be generous (D6a).** `check_workflow_prerequisites.py` owns rows 5/6/13 — no thin orchestrator, no gate logic in markdown. Standalone + `--yes` = exit 3 with one `[PREREQUISITE_UNMET]` block naming *both* fixes (apply first, or `--skip-prerequisites`) in absolute paths and D5a-shaped commands; `--skip-prerequisites` = `[PREREQUISITE_SKIPPED]` + a recorded skip through the same `--skip --reason` state path (surfacing downstream as one `[PREREQUISITE_SKIPPED_UPSTREAM …]` line, never re-asked); inside the workflow, `ensure_prerequisites(..., in_workflow=True, apply_runner=…)` runs the missing apply phase **once** and re-checks — a second unmet re-check is exit 3, not a retry. Nothing is produced before the gate. **`full_workflow_orchestrator.py` is the caller that injects `apply_runner`** (applying suggestions needs the agent's subagent channel) — for row 5 via `generate_tasks_orchestrator.run_generate_tasks(..., in_workflow=True, apply_runner=…)` and for row 6 before it dispatches `implement`. The runner is supplied only under `--yes` (the auto-run is the *unattended* resolution) and is bounded to **one auto-run per phase per run**: a second request for the same phase is refused and the gate ends at exit 3. - **A code reviewer gets its scope and its diff as files, and its prompt says what it can do with them** (plan `review-run-scope-salvage-and-failure-visibility`). `review-code` resolves one scope (`resolve_review_scope`: `--files`/`--files-from`, then `tracked_files`, then the loud `git diff` fallback with `[SCOPE_FALLBACK]`/`[SCOPE_LARGE]`), orders it source → tests → fixtures → generated with the single classifier `git_utils.classify_review_paths` (`code_review.collapse_paths` in `providers.yaml` configures the fixture/generated globs), and before dispatch writes `code-review/review-scope.md` plus one whole, uncapped `code-review/diff/<n>-<slug>.diff` per source/test file (`write_review_diff`; git failures degrade coverage to `partial` with `[DIFF_FAILED]`/`[DIFF_PARTIAL]`, never the phase). `.review-scope.json` records which scope id each result reviewed, so a resume re-runs a result from another scope (`[SCOPE_CHANGED]`, old file kept as `.stale-<id>`). Every Lane A review template also carries `{working_limits}` (`render_working_limits`: the attempt's real minutes, no suites/builds, no unobserved test claims), which names no shell command because `{diff_access}` alone decides that.

The plan, the task list its `TASKS_FILE` marker names (a Markdown file only) and what of its output folder is the workflow's (`output_handler.workflow_file_entries`: the whole folder only when everything in it is; beside code of the plan's name only `state.json`, the prior-changes log, the phase folders and its own temp/lock files — fix round 8) are left out of the census, of `--touched`, of `--only-touched` and of review-code's scope (`resolve_review_scope`'s tracked branch and git-diff fallback; `--files` stays exact), each drop printed once (`Left out N of the workflow's own file(s)`). Implement's first run (no `head_before_implement` yet) re-takes the dirty-tree baseline an apply phase recorded at its own start, before it edited the plan (`record_pre_existing_changes`).
- **Usage is reported or absent, never zero** (`parse_usage`, D3j): claude-code reads the `result` envelope `parse_output` discards, codex the terminal `turn.completed` event, opencode the **sum** of every `step_finish` part (reading the last step alone under-reports a multi-step run). Every other adapter declares `usage: none` and records duration only; a batch mixing the two reports the partial sum plus `tasks_without_usage`.
- **opencode supports its newest release only, and moving it is one command.** `OpenCodeProvider.min_version` equals `verified_version`, the newest `opencode-ai` on npm, and `engines.opencode`, the package README, the container's `opencode-ai` pin (`package.json`, `package-lock.json`, `cli-versions.lock`) and the mock's `--version` name the same release (`tests/test_opencode_version_pins.py` fails otherwise). Tests reach the captures through `tests/opencode_fixtures.py`, so a red parser test after a bump is the release's change to review, never a reason to re-pin; then `make e2e-image` and re-seed the opencode row of `tests/container/cli-surface.yaml`.
- **A runner never inherits the skill's own Python environment** (fix round 8). `uv run --project <skill dir>` exports `VIRTUAL_ENV` naming the skill's venv, and a forwarded or image-wide `UV_PROJECT_ENVIRONMENT` can name it too; `providers.base.build_child_env` (both lanes, the codex jail, the verification command) drops either when it resolves to the running interpreter's `sys.prefix` (`skill_environment_names`), so a subagent's `uv run`/`uv pip`/`poetry` in the user's repository uses the repository's own environment; a value naming another environment is kept. ## Common Pitfalls

- Use `--project` not `--directory` with `uv run` (path duplication bug)
- Never redefine a cross-cutting flag locally: `--host`, `--yes`/`-y`/`--non-interactive`, `--interactive`/`-i`, `--detach`, `--exec-subagents`, `--skip-prerequisites` come from `cli_common.build_parent_parser()`. Adding one to an orchestrator parser that already includes the parent raises `argparse.ArgumentError` at import of the parser, not at first use.
- A new mode is a row in `modes.py`, never an edit in twelve places — but the `argument-hint` **trailer** (everything after the mode alternation) is a literal, so a mode that introduces a new *flag* still needs that constant updated. Regenerate `tests/golden/*_help.txt` whenever the shared parent's help text changes.
- Group IDs are 16-char hex content hashes — use `state_manager.py` hashing, don't generate random IDs
- All output paths are plan-relative for portability
- **A model's words in a bounded line go through `utils/text_clip.clip`, never a bare `text[:n]`** (fix round 22, live run 9 #4: "… would reverse that dec)", "(… 60 m/s), )", "… but scripts/c)" reached `status`, the notice and a host's reply). It cuts at a word boundary, ends in "…", drops a dangling separator and closes any bracket or quote the kept part opened; the budgets stay each surface's own, the OpenCode stop title mirrors it in `capTitleLine` (a parity test holds them together), and `plain_line` lives beside it.
- Validation statuses: `valid`, `invalid`, `needs-human-decision`, `validation_failed`
- Importance levels: HIGH > MEDIUM > LOW
- **Grouping tracks meaning, not word count (2026-09-11).** `suggestion_processor.compute_similarity` is `0.33·title + 0.53·body + 0.08·reference + 0.02·type + 0.04·title-rarity` over normalized tokens (inline code spans tokenized like prose — a backticked identifier is the most specific thing a reviewer names — camelCase/dotted identifiers split, stopwords and review boilerplate removed, suffix-stemmed) weighted by IDF over the set being grouped — which is what demotes a plan's own subject word without a per-project stopword list; the reference channel is scaled by section rarity (a flat bonus handed every pair inside the review's biggest section the full 0.08, exactly where the near-threshold false pairs live), the title-rarity channel is the IDF mass of shared title tokens above `TITLE_RARITY_FLOOR` and is inert on small sets by construction, and two findings naming different files never merge (path-suffix aware; a file is evidence of difference only). `group_similar_suggestions` is agglomerative average-link (merge the closest pair, average over all cross pairs, stop at `DEFAULT_SIMILARITY_THRESHOLD` 0.20 — the safe band on the 2026-09-13 review is 0.196–0.205; below it a third finding joins a coherent pair, above it one comes apart), so it is order-independent by construction and cannot chain. The misses that remain on that review are structural, not tuning: a pair whose members each prefer a different neighbour cannot land in one group under average-link without the chaining the design rejects. A group's `theme` is `summarize_theme` (60-char budget, word-boundary cut, `…` only when cut) but `state_manager.generate_group_id` hashes the theme at the legacy 50-character cut, so a display change is not an identity change and the container goldens' baked ids hold. The old `0.3·title + 0.5·desc + 0.2·(type match)` bag-of-words with greedy single-link at 0.4 was uncorrelated with meaning: on a real 56-suggestion review it filed "activation semantics undefined" with two opponent-parity findings (the 0.2 type bonus was half the threshold) while nine obvious clusters stayed split across 23 groups; the new rules give 28 coherent groups where it gave 46. Every e2e fixture groups to byte-identical `group_hash` lists under both, so no golden moved. `html_report_generator.split_section_refs` files a group under every section a member cites — a composite `reference` such as `## Design Requirements / ### 7. Lap Integration` is split on a delimited ` / ` or `, ` (a bare slash is part of a heading), so per-section counts no longer under-report.
- Reaggregation globs `{phase_dir}/*.json` and treats each file as a per-model result list. Non-model JSON files written into a phase dir (e.g. `report_data.json`, `subagent_batch_report.json`, `state`, `.status`) MUST be added to every `exclude_patterns` list (`review_orchestrator_base.py` — two sites — and `code_review_orchestrator.py`) or they get parsed as suggestions and crash reaggregate. The executor's per-attempt diagnostics escape this by living in a **directory** (`{phase}/failed/`), which the glob never matches. Detach's artifacts are invisible to it by construction — `.status.json` because `glob` skips leading-dot names, `orchestrator-run.log` and its rotated `orchestrator-run.<run_id>.log` siblings by extension — and a regression test in `tests/test_status_file.py` pins that rather than assuming it. **Only the recorded reviewers are read** (fix round 24, live run 10: pi wrote `…deepseek-v4-flash.json` for `…deepseek-v4_1-flash.json`, the slot recorded it failed, and `--reaggregate` then loaded the file as a third reviewer by its stem): both reaggregates pass the glob through `utils/result_files.set_aside_unrecorded_results`, which keeps a file only when its stem is the anchored or pre-anchor stem of a model `.status.json` records (`models_requested`, else `models_completed`; with neither, every file is read as before) and renames any other JSON array `<name>.set-aside` (never deleted), named in a `[RESULT_SET_ASIDE]` line, `.status.json`'s `result_notes`, `progress.notes` (so `status` and a terminal poll's `notice` carry it) and report.md's `**Result files:**` line; and a slot whose requested file is missing reads the one fresh JSON array its provider prefix wrote elsewhere in the phase dir during the call, when no other model of the run shares that prefix, and renames it to the requested name (`invoke_with_file_output`'s `run_model_specs`, `[RESULT_FILE_MISNAMED]`, same surfaces).
- **A per-model result list is not guaranteed to hold objects, and every aggregation site stamps one.** `issue["model"] = model` / `s["source_model"] = model` are item assignments, so a single non-dict element raises `TypeError` and loses every OTHER model's findings with it. Measured 2026-09-20: the stdout fallback scraped the `[0]` out of a clean reviewer's prose sentence "`unattended.ROWS[0].site` correctly left as-is" instead of the `[]` it ended on, `validate_code_review_issues` warned `'[0]: expected object, got int'` and nothing acted on it, and a five-model `review-code` phase died in aggregation with the other four models' eleven findings unwritten — `--reaggregate`, the documented recovery, died at the same statement one function over. Both halves are now closed: every stamping site (`code_review_orchestrator`'s three, `review_orchestrator_base`'s two, `suggestion_processor.extract_suggestions_from_review`) filters through `schema_validator.drop_non_record_entries`, which warns on stderr naming the model and the element and lets the run continue; and clause 5 of `json_extractor.extract_json_from_text` ranks candidates as records → empty document → array of bare scalars, so a bracketed index in prose can never outrank the `[]` a reviewer that found nothing really wrote. Candidates parse with `strict=False` (`_loads_reply`, 2026-10-05): a raw control character inside a string no longer fails the document and serves a fragment from inside it.
- **Nothing durable stores a skill-dir-absolute command.** The plugin cache is keyed by commit hash, so the skill dir moves on every update. `{phase}/.status.json` records `reaggregate_mode` + `plan_file` + `replay_flags` (`cli_common.durable_reaggregate_fields` — the caller's selection flags as a *list*, never a resolved panel and never a command string) and readers rebuild the command from the *running* skill dir through `cli_common.retry_command` (`detach.resolved_reaggregate_command`, which is what `status --view run` prints). A stored flag list is spliced back verbatim, never validated against today's parser: dropping an unrecognized `--quick` is how a retry widens to `defaults.models`. One flag is left out by meaning rather than by name: in an apply phase or `full`, a replay carrying `--yes` or `--detach` drops `--agent-decide`, which `--yes` already sets (`cli_common.drop_implied_judge_flag`; racing run 4: a tool result offered the resume as `--agent-decide --resume` beside a `resume_command` of `--resume`). `implement`'s `--human-task` answers are never replayed either (`cli_common._REPLAY_DROP_ANSWERS`, also off a stored list): `state.json` keeps them and a plain `--resume` applies them, and a replayed answer for a task no longer `failed` is refused (fix round 14). An answer answers one stop: the first status written for its task that the answer did not write (`state_manager._consume_answer`, in `update_task_status_in_state`, so both legs) drops it, and `--task <id>` does not apply one recorded for that task (fix round 15). Printing a resolved path is fine — it is session-scoped; persisting one is not. Both places the review base prepares validation tasks pass `orchestrator=<the phase's own script>`: the fan-out call omitted it (measured 2026-09-14), `prepare_batched_validation_tasks` defaulted to review-plan's, and a failed review-tasks run told the session model to re-invoke `review-plan --reaggregate`.
- **Adding a decision point without its flag is a review error.** A new gate needs a row in `utils/unattended.ROWS` (site id, modes, disposition, where it is enforced), a `DECISION_FLAGS` entry whose parser really accepts it, the resolution written into `instructions/full-workflow.md` *and* the mode file, and — if it auto-resolves — a `record_resolution` call. `tests/test_unattended.py` asserts all four; `tests/test_unattended_e2e.py` then re-runs every standalone mode under `--yes` with **stdin at /dev/null, no TTY and `gum`/`fzf` replaced by tripwires**, so "zero prompts" is observed rather than inferred from the absence of an `AskUserQuestion` string.
- `generate_html_report` persists `{phase_dir}/report_data.json` (the assembled report data) so the apply phase can overlay human/judge decisions onto it and re-embed via `html_report_generator.py regenerate-decisions` — no reconstruction of runtime inputs (diff_data, base_ref, models). `regenerate-decisions --apply-phase` accepts either an apply phase's mode word or its `phase_name` (`html_report_generator._APPLY_PHASE_STATE_KEYS` normalizes `apply-code-fixes` → `apply-fixes`, the one apply phase where they differ), matching `state.json`'s `human_decisions_{phase_name}` key the orchestrator actually writes. `regenerate_report_with_human_decisions` returns `(report_path, matched)`, not just the path (F2, 2026-09-16): a report whose groups carry no `groupHash` (the code-review main path used to hand the validators and the merge step an un-stamped copy of `grouped` instead of the `stamp_stable_ids`-stamped `grouped_list`) used to overlay decisions onto nothing and report success anyway; both callers now print matched-vs-read and warn when they differ. `output_handler.PHASE_DIRECTORIES` and `utils/prior_changes.PHASE_ALIASES` carry the same `apply-code-fixes` → `apply-fixes` mapping so `status --phase`/`--abort`/`--sweep` and `prior_changes.jsonl`'s `append`/`render` resolve either spelling to the one phase (F1/F6, 2026-09-16) — `full_workflow_orchestrator.WRITE_PHASE_DIRS` was previously the only place that held it.
- **`code-review`'s `report.md` numbers ISSUES; every checkbox on it acts on a GROUP** (F1/F5, 2026-09-16). `generate_review_report` is the one report generator that iterates raw issues, so a consensus finding is rendered once per model — and `apply_code_fixes_orchestrator` used to index `self.groups` with those `### N.` numbers: measured on a 12-issue / 9-group review, 11 of 12 `- [x] Skip` / `Mark valid` / `Mark invalid` / `Let the agent decide` marks landed on a different finding and the last three fell off the end of the group list unreported — the user suppresses one fix and silently suppresses another while the one they meant still runs. Both sites (`parse_skips_from_report`, `apply_group_validation_overrides`) now resolve through `_group_hash_for_issue` → the `issue_to_group_map` `post_load_hook` already builds for the edited-description path, match `self.merged` by `group_hash` rather than by position (so `--resume`'s filtered list cannot re-key them either), warn instead of dropping a number the map cannot place, and take `invalid > needs-human-decision > valid > judge_decide` when two members of one group are marked differently. Without issues.json the legacy 1:1 reading survives, which is correct only when no two models agreed. The report says so rather than leaving it to be inferred: a `**Groups:** N` header line beside `**Total Issues:**`, `(of N groups)` on the validation line, `_Same finding as #7, #11 (3 models agree); marking any marks all._` on every member of a multi-member group, and `(group verdict)` on the badge those members share — counting the rendered badges used to give 10 Valid / 1 Invalid / 1 Needs Review over a 7/1/1 validation line and a 12-issue header, three sets of numbers none of which reconciled without `grouped.json`. The numbering itself does not move: `build_issue_to_group_map` and the parser's `### N.`-plus-next-line contract both depend on it — and that contract is now enforced from both ends (F6, 2026-09-16): `_format_issue` flattens newlines out of the title (a `\n` in one pushed the Skip box off the header line and lost the tick silently), and `report_parser` accepts a header only at column 0 after a blank line or the `---` rule, so a rendered description containing its own `### 2.` plus a ticked box cannot forge a skip on an issue the user never touched.
- **A provider log describes the invocation's final outcome, and names its provider.** `llm_client._save_log` writes `<PROVIDER> LOG` from the spec's provider prefix (`CLAUDE-CODE LOG`, `CURSOR-AGENT LOG`, …) with `Success:`/`Error:` for the outcome the caller actually got, plus `Result source: file|file_extracted|stdout_fallback` and, when the stdout extractor lost, either `Stdout parse: failed (<reason>)` (a real double failure) or `Stdout: not used (file output)` when `result_source` is one of `FILE_WRITTEN_SOURCES` — a file-output provider was told not to print JSON on stdout at all, so its failed stdout parse is expected, not a fault worth flagging beside `Success: True` (F9.2, 2026-09-16). `invoke_with_file_output` defers every exit-0 write, not only a parse failure (`_defer_parse_failure_log` → `details["_deferred_log"]`), and writes once, after the file-vs-stdout channel is resolved, via `_finalize_file_output_log` — until 2026-09-11 a claude-code review that completed through the file channel with 24 suggestions logged `Success: False` / `No valid JSON found in text` under a header that called it cursor-agent; until F13 (2026-09-16) a *clean* stdout parse wrote its log immediately, before the channel was known, so `Result source:` was silently absent for exactly the runs that used the stdout fallback. Hard failures (timeout, non-zero exit, launch failure) still write immediately — no channel choice to wait for. The per-model fan-out's `Output file: <path> (source: …)` line (`llm_client.describe_output_file`) only says "Output file" when `source` is `file`/`file_extracted`; a `stdout_fallback` source — the model never wrote there — says "Result will be saved to" instead (F14). The `save_agent_log` that once lived in `review_orchestrator_base` had no callers and is gone.
