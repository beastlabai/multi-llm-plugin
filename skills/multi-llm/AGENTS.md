# Multi-LLM Skill — Development Guide

## Architecture

- Orchestrators produce JSON instructions for Claude Code to execute — they never modify code directly
- **`multi_llm.py` is the single entrypoint.** Every mode is `uv run --project <skill-dir> -- python <skill-dir>/multi_llm.py <mode> [<positional>…] [--host <id>] [mode flags…]`, so a host shim resolves one path once and routes nothing itself. `<mode>` is a bare word and must be `argv[1]`; unknown/missing is exit 3 listing the valid modes. Positionals are normalized into the flags the target already parses (plan modes `<plan>`→`--plan-file`; `ask` `<plan> <question>`→`--plan-file` + `--question`, falling back to a dispatcher-written `--question-file` past `MAX_ARGV_QUESTION_CHARS`); an extra positional is exit 3. Everything after the positionals is forwarded **verbatim as a Python list** to that mode's `main(argv) -> int`, imported lazily and called **in-process — never `subprocess`** (one `uv` resolution per invocation, a plan path with a space survives by construction, `shlex` never runs on this path). `multi_llm.py <mode> --help` prints the target parser's help. Exit codes are uniform and never remapped: `0` done, `1` unexpected error, `2` nothing to do / phase already complete, `3` needs a human. **What a phase *found* is never an exit code** — findings are artifacts and bracketed stdout markers, so a review that completed is `0` however serious its findings are. `review-code` used to return `1` when it found HIGH-importance issues, which claimed an error that never happened: it stopped `full` at `review-code`, one phase before `apply-code-fixes` (the phase that fixes what the review just found), and put `state: "error"` on the result line of a successful run. It now prints `[HIGH_PRIORITY_ISSUES] <n>` and returns `0`; `--fail-on-high` is the opt-in for a standalone CI gate and is exit `3`, never `1`. Every invocation ends with exactly one machine-readable stdout line, `MULTI_LLM_RESULT: {"mode","phase","state","exit","artifacts":[…],"next":…}`, emitted even on a crash (`next` is `null` when no follow-up is owed). One **optional** key joins them: `consolidation_recommended` (`{valid_groups, threshold, command}`), present only on a review phase that crossed `CONSOLIDATION_RECOMMENDED_THRESHOLD` — written to `{phase}/.status.json` at the same site, carried through `detach.classify_run` and re-emitted (with one rendered line) by `status --view run`, because the `[CONSOLIDATION_RECOMMENDED]` marker is a bare `print` and a detached caller never reads the log: measured 2026-09-16, a 29-group run printed the marker and the session model told the user no consolidation had been recommended. Deliberately **not** `next` — `--consolidate` is one of the dispatcher's `mechanical_continuations`, which the opencode plugin auto-follows without asking, and following a recommendation would run a phase nobody requested.
- **`modes.py` is the one owner of the mode table** — mode words, the closed alias table (`review`→`review-plan`, `code-review`→`review-code`, `tasks`→`generate-tasks`; no prefix or fuzzy matching), positionals, lazy dispatch targets, phase names, core instruction files, and which modes are user-facing. `SKILL.md`'s `argument-hint`, `multi_llm.py --help` and `check_workflow_prerequisites.py`'s `--mode`/`--phase` choices are all **rendered** from it; adding a mode is a row, and `tests/test_instruction_portability.py` fails if the dispatcher and `argument-hint` disagree. Note the one place mode word ≠ phase name: mode `review-code`, phase `code-review`.
- **`utils/cli_common.py`** owns the cross-cutting argparse **parent** (`--host`, `--yes`/`-y`/`--non-interactive`, `--interactive`/`-i`, `--detach`, `--if-not-running`, `--max-detached N`, `--exec-subagents`, `--skip-prerequisites`, plus the suppressed `--internal-worker`/`--internal-run-id` re-entry flags), included by every `*_orchestrator.py` parser plus `check_workflow_prerequisites.py` and `init_config.py`, so a direct invocation accepts the same flags with the same semantics. It also owns skill-dir resolution — `os.path.abspath`, **symlinks preserved, never `realpath`** (`link-skill.sh` symlinks the plugin cache at a dev checkout; resolving would move `uv run --project` off the `pyproject.toml` the host loaded) — plus the printed-command builders, the `MULTI_LLM_RESULT` emitter and the per-invocation record (mode word + normalized argv) a detached child re-executes. It also owns `--dry-run-subagents` (D3l: render every command, start no child). `--exec-subagents` is implemented for the read/analyze phases **and** the four write phases (below); `--detach` covers every long-running mode (below).
- **`--detach` self-daemonizes every long-running mode**: the fan-out modes (`review-plan`, `review-tasks`, `review-code`, `ask`) plus the executor-backed write modes (`apply-suggestions`, `apply-task-suggestions`, `apply-code-fixes`, `implement`) plus `generate-tasks` and `full`, whose orchestrators landed with the Phase-3 sequencing — so the plumbing they registered for is now the plumbing that runs (`generate-tasks` claims `{plan}/generate-tasks/`, `full` claims `{plan}/full/`)). Everything else exits 3 rather than accepting a flag that does nothing. The write phases cross the **same** boundary through `apply_orchestrator_base.maybe_detach_write_phase` / `implement_orchestrator.run_implement_write_phase`, placed after all pre-flight and before the first child, so one spawn implementation and one `.status.json` claim serve both halves; per-task write progress lands under `progress.write_subagents`. One boundary crossing, `utils/review_orchestrator_base.maybe_detach`, sits *after* all pre-flight (flags, inputs, model resolution, phase-dir creation, lock pre-check) and *before* any model or agent CLI runs, so a bad flag or an unconfigured provider fails on the caller's terminal with **no child and no log**. The `--reaggregate` branch of every review orchestrator crosses the same boundary, after its one pre-flight (the phase dir exists): measured 2026-09-14 on review-tasks, that branch ran ahead of the boundary, the re-dispatch of the failed validation batches finished in the invoker's foreground with no run banner, and the opencode plugin — which composes `--detach` on every launch and adopts a run only from the banner — reported the completed run as "the launch reported no run_id on its banner". The invoker forks (POSIX: `setsid` + a second fork, so the worker reparents to init and the invoker has no child to reap; Windows: `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`), waits ≤10 s for the worker to publish its own identity, then prints the log path plus the `status`/`--abort` commands. **`{phase}/orchestrator-run.log` is handed in as the worker's stdout/stderr on both platforms, so it holds the whole worker and not just the part after the boundary** — `process_control.spawn_detached` opens it append-only and dup2s it onto the child's fds 1/2 in the intermediate, and `enter_detached_worker` (which `maybe_detach` reaches only at the *end* of pre-flight) compares `(st_dev, st_ino)` and reopens nothing. Until 2026-09-16 the POSIX leg gave the worker `/dev/null` and the worker reopened the log itself, so every setup line an orchestrator prints on its way to the boundary went on the floor: a completed `apply-suggestions` log opened at `[DETACHED_RUN]` with no `Loaded 33 suggestion groups` and no `No user preferences detected` — the notice under which it applied all 29 items — and `review-plan`'s log had no `Loaded plan:`/`Backup saved:`/`Models:`. The invoker's own copy still goes to the caller's terminal, which is the pre-flight rule; the setup lines therefore sit *above* the `[DETACHED_RUN]` banner in the log, and a worker that dies before the handshake now leaves its reason in the file the launcher's failure message tails. The child re-executes `uv run --project <skill-dir> -- python <skill-dir>/multi_llm.py <mode> … --internal-worker` — **never bare `python`** (`sys.executable` inside `uv run` loses the lockfile and `--project`) — with `--detach`'s implications (`--yes`) written out and paths absolute. `--detach` implies `--yes` and is exit 3 with `--interactive` at parse time. Never combine it with a host's own background primitive: Claude Code uses `run_in_background` and never passes `--detach`.
- **`{phase}/.status.json` is one file with one schema**: today's checkpoint plus two reserved objects, `run` (the process machine `starting → running → {done, failed, aborted}`, heartbeat, pid + `process_start_time` identity, `exit_code`, `error`, `resolutions`) and `progress` (display only). `run.state` is **not** the top-level `state` (the phase machine resume reads) — a crashed fan-out is both. `progress.models_done` is written by the fan-out that owns the models: the review base advances it to `len(model_specs) - len(failed_models)` beside `models_completed`, and `code_review_orchestrator` does the same at its own `models_complete` write and, since 2026-09-16, via a `slot_finished()` of its own inside `run_all_reviews` (mirroring the base's) — before that fix its fanout step wrote `models_done=0` and nothing advanced it until the last model returned, so a mid-run poll of a finished-in-part run read `models 0/3` beside three completed reviewers. **Progress is reported while it happens, not only at the end of a stretch.** `run_all_models` advances `models_done` per finished *slot* (a failed or skipped slot included — the recomputation at `models_complete` is what turns slots back into successes), `dispatch_subagent_tasks` reports the step its batch is on before it dispatches (`validating`, `revalidating`, `consolidating`, else `dispatching <label>` — `_DISPATCH_STEPS`), and both executor mirrors write per finished task rather than once at the end (`subagent_executor.run_tasks` counts against the batch's full size; `write_batch_scheduler._run_batch` takes its `finished_in_batch` rows under a lock because a disjoint group dispatches on threads — `in_flight` in the same mirror now names the opposite, a dispatch started and not yet classified, F10). Measured 2026-09-16 on a 516 s `review-plan`: 435 s of fan-out reported `models 0/4` and 62 s of validation reported `grouping`, leaving ~5 s of the run with an informative progress line. Primitives live in `utils/status_file.py` (re-exported by `review_orchestrator_base` as `write_status`/`update_status`, so nothing about the write path changed) because `status` must stay sub-second; `run`/`progress` merge key-by-key like `output_files`, a plain `write_status` cannot erase them, and every write after the worker's initial claim is **compare-and-set on `run_id`** so a closed-out run can never resurrect itself. Liveness is the heartbeat (10 s; expired at 60 s = six missed beats); `{phase}/.lock` (`utils/process_control.py`: `flock`/`msvcrt`, held on an open fd) makes one writer per phase dir, and a second run against a live holder is exit 3 naming it. Every run ends in exactly one terminal state with `run.exit_code` recorded — the worker records its own (nothing is its parent after the double spawn), and `status` closes out `failed(heartbeat_timeout)` with `exit_code: null` when the heartbeat expires and the identity probe says the process is gone. The machine's middle word is written too: both sites that materialize `validation_tasks.json` write `state: validation_pending` beside the `validating` progress step, which `status` used to print as `phase state: grouping_complete` / `progress: validating` for the whole validation stretch. **The phase machine's terminal word is `complete`** (2026-09-11): `run_review_orchestration`, `reaggregate_from_existing_files` and `code_review_orchestrator`'s three completion sites write `state: complete` and `progress.step: complete` right after `mark_phase_completed`, so `status` shows a finished run as finished — before that the last checkpoint the fan-out wrote (`grouping_complete`) stayed on disk forever and the status view read a done run as still grouping. No reader gates resume or reaggregate on the exact word; `state.json`'s `phases_completed` remains the record that matters.
- **`utils/unattended.py` owns the unattended contract (D6): fifteen decision *sites*, three dispositions, no questions.** `ROWS` is the closed table — each site keyed by a stable `site_id`, the modes that reach it, the disposition it lands on (**auto-select** / **fail closed** / **explicit flag** — "ask in free text" is not a fourth option) and where it is enforced; `DECISION_FLAGS` is the D5a input contract, one flag per row whose values enumerate exactly what a question would have rendered. **Exit 3 is reserved across every mode for "unattended run cannot proceed"** (missing uv, unmet prerequisite, contradictory or empty decision flag), distinct from the exit-2 phase-already-complete guard, so a host can tell "needs a human" from "already done". `validate_decision_flags(argv)` runs in the dispatcher *before* any parser so `--models ""`, `--human-task <id>=` and an unknown `--force-strategy` are exit **3** at parse time rather than argparse's exit 2; `choices` on each parser is the second layer. `record_resolution(phase_dir, site_id, decision)` prints `[AUTO_RESOLVED] <site>: <decision>` and, under `--detach`, appends to `run.resolutions` via `detach.record_resolution` → `status_file.append_resolution` (a foreground `.status.json` still gains no new keys). Auto-resolutions are announced only under `--yes`, so with `--yes` unset a run is byte-for-byte what it was. **The apply phases' own two sites (rows 10 and 11) are recorded, not just taken**: both fire *before* `run()` crosses the detach boundary, where no run handle exists yet and `detach.record_resolution` is a silent no-op — so `ApplyOrchestratorBase._record_resolution` prints the marker at the site and `_flush_resolutions` replays the entries into `run.resolutions` immediately past the boundary. One leg prints it: under `--detach` the invoker reaches both sites and then re-executes itself as the worker, which reaches them again, so the marker is skipped on the leg that is about to fork (`_is_detach_invoker`) and kept on the one that writes the record. Row 11 is not taken at all under `--dry-run` — that flag is itself one of the nine that bypass the no-selection confirmation, and the run it describes as "apply all valid items" applies none. Measured 2026-09-16 on a `--yes --exec-subagents` apply-suggestions run: 29 of 33 groups were applied because nobody had selected anything, `.status.json` said `"resolutions": []`, and the row-11 decision left no trace in the log, the payload or the status view. `--yes` also now *implies* `--claude-decide` in every apply phase (`apply_orchestrator_base.apply_unattended_defaults`) and resolves the human-task strategy to `skip-dependents`; it **never** implies `--skip-prerequisites`.
- **Python never sniffs its host (D6b).** No `isatty()`, no `CI=` read, no `--print` detection: interactivity is *requested* (`--interactive`), never detected, so the same argv produces the same phases in a terminal and in a pipe. `utils/interactive.is_tty()` is gone and `resolve_models(..., unattended=True)` never reaches a picker — it returns `defaults.models` or raises `NeedsHuman` (exit 3). `full-workflow.md`'s "no TTY → skip review-tasks" branch is deleted. `tests/test_unattended.py` parses every runtime module's AST (so a *comment* about `isatty` is not a call) and fails any reintroduction; the one allowlisted `isatty` is `utils/metrics.py`'s ANSI-colour gate, which decides how a line looks and never which phases run. `--yes` with `--interactive` is exit 3, never precedence.
- **The prerequisite gates are the one place `--yes` must not be generous (D6a).** `check_workflow_prerequisites.py` owns rows 5/6/13 — no thin orchestrator, no gate logic in markdown. Standalone + `--yes` = exit 3 with one `[PREREQUISITE_UNMET]` block naming *both* fixes (apply first, or `--skip-prerequisites`) in absolute paths and D5a-shaped commands; `--skip-prerequisites` = `[PREREQUISITE_SKIPPED]` + a recorded skip through the same `--skip --reason` state path (surfacing downstream as one `[PREREQUISITE_SKIPPED_UPSTREAM …]` line, never re-asked); inside the workflow, `ensure_prerequisites(..., in_workflow=True, apply_runner=…)` runs the missing apply phase **once** and re-checks — a second unmet re-check is exit 3, not a retry. Nothing is produced before the gate. **`full_workflow_orchestrator.py` is the caller that injects `apply_runner`** (applying suggestions needs the agent's subagent channel) — for row 5 via `generate_tasks_orchestrator.run_generate_tasks(..., in_workflow=True, apply_runner=…)` and for row 6 before it dispatches `implement`. The runner is supplied only under `--yes` (the auto-run is the *unattended* resolution) and is bounded to **one auto-run per phase per run**: a second request for the same phase is refused and the gate ends at exit 3. With no runner, workflow mode behaves like standalone. **Streams:** this script's stdout stays pure JSON (callers `json.loads` all of it) and its `[PREREQUISITE_*]` blocks go to stderr + the JSON's `message`; `implement_orchestrator.py`, whose stdout is already prose+markers, prints its own on stdout.
- **The uv bootstrap is split across three layers (D6c), and the wording lives in `hosts/uv-missing.txt`.** `install-host --check` (install time) and each rendered shim's `command -v uv` preflight (invocation time — the only host-side logic that cannot be Python) are D7's; the **Python backstop** is `unattended.require_uv()`, run by the dispatcher before every mode for the cases the first two cannot cover (uv removed after install, a host calling `multi_llm.py` directly, a hand-edited shim). Same message, same exit 3, never an install, and **no `python3 -m` fallback ever** — dependencies are pinned in `uv.lock`, so a bare interpreter turns "install uv" into a `ModuleNotFoundError` or a silently wrong version mid-fan-out. `references/uv-check.md` is the shim-side contract and points at the message file; **`utils/detach.resolve_uv()` delegates to `unattended.find_uv()`** rather than keeping its own probe — it used to carry a hand-written two-entry list — the two home-relative locations only, with no `.exe` variants, no Homebrew and no system paths — and name that shortened list back to the user in its own error text, so the detached path every fan-out mode goes through could refuse on a machine where the foreground preflight had just succeeded. `tests/test_uv_candidates.py` owns the parity: nine readers, each asserted element-for-element **and in order** against `UV_CANDIDATES`, plus a discovery half whose `git grep` hit set must *equal* the reader table — so a tenth reader goes red on the PR that adds it, rather than drifting silently.
- **`utils/unattended.uv_run_args()` is the single owner of the `uv run` flag list**, and the flags are `--frozen --no-dev`. `--no-dev` is the load-bearing half: `--frozen` suppresses only the lockfile *staleness check* and does not stop the sync, and `uv run` syncs the **dev** group by default — measured against this tree, `--frozen` alone installs 17 packages (ruff, pytest, jsonschema…) where `--frozen --no-dev` installs one (pyyaml), so without it a first dispatch pulls the whole dev group and every offline posture fails on a package it never needed. Baking it in is non-destructive: `uv run --no-dev` against a dev-synced environment leaves those packages in place and installs only what is missing (only `uv sync --no-dev` would remove them, and nothing on these paths calls it). Four consumers read that one owner — the foreground launcher, `cli_common.dispatcher_prefix()` (every printed follow-up and every `MULTI_LLM_RESULT.next`), `detach.build_child_command()` (the worker re-exec) and `cli_common.render_instruction_text()` (the `{UV_RUN_FLAGS}` token every command in `instructions/*.md` and in each `hosts/*/shim.md.tmpl` carries, so the file route's verbatim runbook text cannot dispatch with a different flag list than Python does) — plus one deliberately hand-typed spelling: Claude Code's `SKILL.md` is read **raw** by the host (it expands `${CLAUDE_SKILL_DIR}` itself at load time), so a token there would reach an agent unsubstituted while a flagless `uv run --project` would put the first-run dev-group sync on the host that runs most — it therefore writes `--frozen --no-dev` out, and `test_instruction_portability.TestTheClaudeShimSpellsTheFlagsOut` compares that copy back to `uv_run_args()` element for element so it cannot drift (those two shim-level commands are consequently pinned to the *default* list; the core the shim loads at step 4 is rendered and does honour `MULTI_LLM_UV_RUN_ARGS`). The maintainer invocations below (`uv run --project skills/multi-llm -- pytest`) are outside the rule on purpose: they want the dev group. Only the first consumer was ever asserted, which is how the worker came to re-exec with **neither** flag: a careful `--detach`ed launch handed off to a child that recreated the 17-package sync in a log where nobody would see it. `child_env()` also exports the resolved `MULTI_LLM_UV`, so the worker re-resolves to the binary the preflight approved instead of re-probing a `PATH` a detached session may not share. `MULTI_LLM_UV_RUN_ARGS` **replaces** the list and never appends — that is what makes `--no-sync` expressible at all — so it can legitimately drop `--no-dev`, and blank or whitespace-only behaves as unset.
- **`utils/process_control.py` is the only place `fcntl`/`msvcrt`/`ctypes` process internals appear** (locking, liveness, creation-time identity, process-group/Job Object teardown, the detached spawn). It is the façade `plans/windows-macos-portability.md` owns; per that plan's sequencing rule this work typed it first, so its signatures are a cross-plan interface. A test fails any other runtime module that imports `fcntl` or `msvcrt`.
- **`util` namespace, not a user-facing surface**: `multi_llm.py util metrics|prior-changes|report|decisions|update-tasks|prereq|finalize-tracking|backup|restore-batch|runs|instructions …` routes the utility scripts the same in-process `main(argv)` way, flags forwarded verbatim. Excluded from `argument-hint` and from `--help`'s mode list, documented only under `multi_llm.py util --help`, and — like the reserved hidden `--internal-*` prefix — never rendered into a `MULTI_LLM_RESULT.next` value. `util instructions <mode>` prints a mode's core instruction file with every skill-dir placeholder replaced by the running skill dir, so the text a host agent reads carries no unexpanded token. `util finalize-tracking` also inserts the implementation summary's back-reference into the plan when `--plan-file`/`--summary-file-relative` are passed (it replaced an inline `python -c` in `instructions/implement.md`, which was a second skill-dir substitution site and a block of code for an agent to retype).
- **`SKILL.md` is the Claude Code *shim*, not the contract (D5c).** ~107 lines: the skill-dir binding, the uv preflight, the flag→mode-word convention, the `util instructions <mode>` read step, the three baked verb sentences, the one dispatcher command with `--host claude-code`, and worked examples. Everything else moved — the workflow to `instructions/`, provider configuration to `docs/providers.md`, the standard report shape to `references/summary-format.md` — and the argv-scanning shell preamble is **deleted**: it re-implemented `modes.py` plus the dispatcher's own positional normalization in a shell syntax only one host runs, and the dispatcher already rejects a bad plan path or an empty question with exit 3 naming the token. Its three verb sentences are **byte-identical** to `host_capabilities.verb_sentences("claude-code")` — asserted by `tests/test_shim_correctness.py`, because `installable: false` means nobody renders this file and the reference host would otherwise be the one host free to drift from the data that governs the others. That test is parametrized over every shipped shim (line budget against `shim_max_lines`, no unfilled slot, no deferral to the agent, no env assignment beyond `MULTI_LLM_SKILL_DIR`, no core paragraph copied in, every named mode resolving through the real parser), so the per-host `.tmpl` files pick it up with no edit.
- **`hosts/capabilities.yaml` is the verb→mechanism map, and it is data (D5b).** One entry per host id, validated against `schemas/host_capabilities.schema.json` (every field required except a closed set of lint/doc keys — `shim_max_lines`, `headless_invocation`, `package` — each admissible only because it governs a lint or a generated document and never a dispatch decision; a defaulted *capability* is the silent guess the schema exists to remove). `subagents`/`ask`/`detach` are the three verbs; `native_tool` is a per-verb map and **the only place a host tool name is allowed to exist** outside a shim. Every value carries a `provenance` (`verified`|`documented`|`unknown`) and **a `documented`-only value never selects the non-conservative path** — Codex and OpenCode ship `subagents: executor` and `detach: python`/`required` for exactly that reason, and a test enforces it. Read through `utils/host_capabilities.py`: `resolve_host_id()` is `--host` → `$MULTI_LLM_HOST` → `claude-code` (declared, **never sniffed**), an unknown id is exit 3, `require_executor_runner()` makes `--exec-subagents` exit 3 on a host whose entry declares no `agent-readonly`/`agent-write` runner, and `verb_sentence()` renders the one fixed phrasing per enum value that a shim bakes in. `subagent_executor.effective_ceiling()` takes the host leg of D3i's minimum from the same entry. `references/host-capabilities.md` is **generated** by `hosts/render_capabilities.py` (`--check` is the CI staleness guard, byte-compared); `hosts/snippets/*.md` are the host-independent shim partials (uv preflight, `--detach` poll loop) `install-host` interpolates into any template that carries their slot — the two shipped shims carry neither, because a 100-line rendered budget cannot hold uv-preflight's inlined 31-line install message *and* the poll loop, so both name `hosts/uv-missing.txt` and print it exactly as the reference shim does. **Nothing here is on an agent read path** — a test asserts no instruction file, reference or shim names either the YAML or the generated markdown, because an agent reasoning over a capability matrix mid-run is a worse failure mode than the one the verbs remove. `utils/unattended.INVENTORY` is D5d's closed per-`ask`-class inventory over the same rows, with one renderer (`render_option_block`) serving both presentations and refusing the fail-closed rows.
- **The instruction core is host-neutral, and the three verbs are its whole host vocabulary (D5).** `instructions/*.md` name *spawn subagents* / *ask the user* / *run detached* and no host tool — no `Task`, no `AskUserQuestion`, no `run_in_background`, no `${CLAUDE_SKILL_DIR}` — and every command in them is the one invariant prefix `uv run {UV_RUN_FLAGS} --project "{SKILL_DIR}" -- python "{SKILL_DIR}/multi_llm.py" <mode-or-util>` (two tokens, both substituted at read time — the second from `unattended.uv_run_args()`, because a hand-typed `uv run --project` in this corpus *is* a dispatch without `--frozen --no-dev`). `tests/test_instruction_portability.py` owns both halves: a forbidden-token lint (unambiguous tokens anywhere, `Task`/`Read`/`Write`/… only in their tool spellings, per-file allowlist entries asserted to still match) and the per-file `{SKILL_DIR}` manifest, whose one non-zero `${CLAUDE_SKILL_DIR}` row is `SKILL.md` — the Claude Code shim, where the host expands the variable at load time. Each verb is resolved to exactly one concrete mechanism *in the shim*; the matrix is never on an agent read path. **The way back is `legacy/`**: the frozen pre-refactor tree, served instead of the rewritten core when `MULTI_LLM_LEGACY_INSTRUCTIONS=1` (read path only, Claude Code only, unmaintained — see `legacy/README.md`), so the rewrite can be backed out without reverting the dispatcher, the executor or the unattended work with it. The regression guard is `tests/test_instruction_refactor_guard.py`: a normalized golden bundle of one fully mocked workflow run over `tests/fixtures/e2e/plans/auth-feature.md` × `full_workflow.yaml`, captured on the `phase3-pre-refactor` tag and reproduced with a **zero** diff outside `tests/golden/expected_changes.yaml`.
- **Import must be side-effect free.** Every dispatch target keeps argparse and all work inside `main(argv)`, with `if __name__ == "__main__": sys.exit(main(sys.argv[1:]))` — no module-level argparse, no module-level `sys.argv` read, no I/O at import. Two targets can run in one interpreter, and `tests/test_instruction_portability.py` enforces it (AST guard + a one-process import probe). Direct invocation of `*_orchestrator.py` stays **supported but unadvertised** (the test suite and `--internal-*` re-entry rely on it); the instruction core and shims name only `multi_llm.py`.

The facts every review lane reports the same way — the per-slot `models_done` counter, the deadline back-fill of `failed_models`, the artifact hand-back, and the distinct-HIGH-group count (`high_priority_groups` in `.status.json` and on the result line, for review-plan and review-tasks as well as review-code since 2026-09-17) — are one helper each in `review_orchestrator_base` (`fanout_slot_counter`, `backfill_deadline_losses`, `record_review_artifacts`, `record_high_priority_groups`), and review-code's on-disk batch merge goes through the shared `merge_validation_batches`; none of them is copied into `code_review_orchestrator.py` any more.
- `ask` mode (`ask_orchestrator.py`) is a read-only free-text Q&A side-channel: markdown output, no JSON schema / grouping / validation, output under `{plan}/ask/<question-slug>-<hash8>/`. It shares concurrency mechanics with the review modes via `run_models_concurrent` in `review_orchestrator_base.py`.
- **`implement`'s write phase closes the artifact/resolution/denominator gaps the apply phases already closed for themselves.** `run_implement_write_phase` now seeds every materialized task `pending` in `state.json` before the scheduler loop starts, so `check_workflow_prerequisites`'s task count reads the plan's total rather than however many happened to finish or be skipped so far (F5); records its own artifacts the way `ApplyOrchestratorBase._record_write_artifacts` does, since `implement` never goes through that base (`write_tasks.json`, `write_batch_report.json`, `subagent_batch_report.json`, `summary.md`, `prior_changes.jsonl`, and every `files_touched` path an `ok` outcome names — F7); buffers the row-8 human-task-strategy auto-resolution past the detach boundary the way `_record_resolution`/`_flush_resolutions` do, since it used to fire before a run handle existed and left `.status.json.resolutions` empty under a log that printed `[AUTO_RESOLVED]` (F8); and stamps `write_tasks.json` with `inputs.tasks_sha256` for the plan's external `tasks/tasks.md` (F15). Its `subagent_batch_report.json`'s own `task_file` field used to read `null` on the write path — `run_task_file` fills it from the argument the read path is handed, and `WriteBatchScheduler` takes no such argument — so `_write_report` now names it directly: `write_task_file_for_phase` always persists the same materialized list at `{phase_dir}/write_tasks.json`, which every write orchestrator passes as the scheduler's own `phase_dir` too (N9). 2026-09-16.

## Developer Notes

- **Full model for validation**: Validation subagents use full model capability — never downgrade to haiku. Only the coordinator (simple orchestration) uses haiku.
- **Backup before modification**: Always backup files before any salvage or modification operation.
- **A read/analyze dispatch never gets write access.** An adapter opts into `agent-readonly` by implementing `build_agent_command(prompt, model, profile)` with the runner's **own** denial mechanism (codex `--sandbox read-only`, opencode `--agent plan`, claude `--allowed-tools`/`--disallowed-tools`) and declaring it in `agent_profiles`. There is no fabricated read-only mode: an adapter without one raises `ProfileUnsupported` and is refused as a runner with the reason named. `tests/test_providers.py` (and `tests/test_subagent_executor.py`) cross-check declaration against implementation in both directions, for profiles **and** for `parse_usage`/`usage_support`, so the capability data cannot drift from the code. The write profile follows the identical rule one level up: `agent-write` must agree with `supports_file_edits`, must render a real command, and must offer a non-argv transport — and the set of adapters declaring it is pinned to exactly `claude-code`, `codex`, `opencode`, because widening it hands pre-approved edit access to a user's repository. **The same rule binds `generate`, and the rule is profile-scoped rather than flag-scoped** (§3.5): `build_command` *is* the Lane A review/ask fan-out, and every phase that reaches it — `ask`, `review-plan`, `review-tasks`, `review-code`, task generation, consolidation — consumes a *document*, never a diff. So no adapter may reach a write bypass (`--yolo`, `-f`/`--force`, `--yes-always`, `--auto-approve`, `bypassPermissions`, `--dangerously-*`, `GOOSE_MODE=auto`) from it, which is exactly what cursor's `-f` did before `--trust --mode ask` replaced it. A runner whose only unattended mode is such a flag gets an explicit `None` row in `providers.yaml`'s `read_only_modes:` table **and a named exception recorded beside it** (`bypass_exception:` — the token, the profile, why it survives, what retires it), never a silent precedent; `agy`'s `--dangerously-skip-permissions` and `aider`'s `--yes-always` are the two entries that disposition currently holds, and both are queued behind a probe. `--yolo`-class flags are reserved for a future `agent-write` runner that has **no** native sandbox or permission mode, and none of the three pinned above needs one, so that row is empty today. `tests/test_read_only_modes.py` is the guard and it reads this repo's own source, never a vendor's help text: it scans every registered adapter's `build_command`/`get_env` (plus `agent-readonly`) and goes red on any such token that is not a declared exception — and equally red on a declared exception whose token is gone, so an exception cannot outlive the flag it excuses. **What the profile cannot contain, the prompt has to say.** `agent-write` containment is file-granular and repo-rooted — and for opencode deliberately outside `HERMETIC_PROFILES` (`utils/providers/opencode.py`) — so it saw nothing of the write subagent that stood up a local `http.server`, drove headless Chrome at it for ten of an eleven-minute task, left the server orphaned, and signed off with `killall -9 … python3`, killing the detached orchestrator that had dispatched it (F2, 2026-09-16). The write-batch scheduler's shared result-contract seam (`_with_result_contract`, `utils/write_batch_scheduler.py`) therefore names `kill`/`pkill`/`killall` and background servers/browsers as forbidden and sends verification to static checks on every dispatched write batch (N3, 2026-09-16: `prompts/implementation_task.txt`'s own `## Constraints` used to carry a second copy of the same rule, which also stranded the template's terminal "Proceed with the implementation." ahead of the appended contract — both are gone from the template now, so the shared seam is the only place any write kind picks the rule up), and `implement_orchestrator.ACCEPTANCE_CRITERIA_FRAMING` heads the pasted criteria with whose job they are: a plan's criteria are routinely *manual* verification steps, and nothing marks them as such — `executor_role == "human"` is task-level, not criterion-level. Since N4 (2026-09-16), a human task's own materialized entry skips the framing, the `## Constraints` block and the proceed line entirely: `implement_orchestrator.build_human_task_prompt` renders its checklist plus one "this task is deferred to a human; nothing dispatches it" line instead, because a task whose whole job is the browser/manual work those sections forbid should not read a prompt that forbids it.
- **The fan-out asks each adapter for the channel it actually has** (`supports_file_output`). The three JSON review prompts end in a `{output_location}` block rendered by `llm_client.render_output_location` from the adapter's own declaration, never from a provider name branched on in an orchestrator: `True` (the default) renders the byte-identical "write your JSON output to this file: …" block, `False` asks for the raw array on stdout. The `False` roster is pinned to exactly seven: **five of them are one shape, the sixth is another, and the seventh is a third**. Five run their CLI in a mode that cannot write and refuse in words: `cursor-agent` `--mode ask`, `aider` `/ask`, `qwen-code` `--max-tool-calls 0` (a **zero** tool budget — the abort is `FatalBudgetExceededError`, exit 55, and zero bytes on stdout, so there is not even a fallback left), `vibe` `--agent plan` (upstream's read-only profile, `write_file`/`edit` permission `never`) and, since 2026-08-19, `copilot` — whose flagging atom is `--no-ask-user` but whose real mechanism is the flag it deliberately does *not* ship: with no `--allow-all-tools`, the model calls `create` and the CLI answers `{"message": "Permission denied and could not request permission from user", "code": "denied"}`, and under `-p` no approval channel exists for it to arrive on. A measured `cursor-agent` slot is the archetype: `is_error: false` carrying only "I can't write the requested file while Ask mode is active", then a failure on `JSON parsing failed from both file and stdout`. **`gemini` is the sixth and it is worse**: under this adapter's argv (no `--yolo`, no `--approval-mode`) gemini-cli ships **no `write_file` tool at all** — nine tools, none of them a write — so handed one it errors internally (`Tool "write_file" not found in registry`), writes nothing, and **exits 0 printing the model's own "JSON written to …" confirmation as its answer**. A refusal fails loudly; this reports success for a write that never happened, so the slot would record the confirmation sentence as the review. **`codex` is the seventh (D6, 2026-09-11) and its reason is the machine, not a mode**: `codex exec` writes through bubblewrap, and on a stock Ubuntu 24.04 (`kernel.apparmor_restrict_unprivileged_userns=1`) bwrap cannot start (`bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`), so a review asked for a file spent seven minutes twice, failed three writes and returned no JSON — while the array was its final `agent_message` all along, which `parse_output` reads. The fan-out asks it for stdout; `supports_file_edits` stays `True` because the agent-write profile really edits, and the model-free sandbox probe that gates it is D6 step 3. muse, the other bubblewrap user, runs `--disable-sandbox` instead (beside `--disable-approval`, and never `--yolo`, which also grants workspace trust). **The prompt is the fix, never the argv**: restoring `-f`/`--yolo` to buy the file write back is the write bypass §3.1 removed. Nothing on the parse side moves — `invoke_with_file_output` still reads the file first, and `save_model_result` writes the per-model result file from the returned data whichever channel supplied it. The roster is not maintained by hand: `tests/test_provider_housekeeping.py::TestReadOnlyArgvMatchesTheDeclaration` reads every adapter's rendered argv, and any restriction-shaped atom in it (`ask`, `plan`, `read-only`, `no-write`, `sandbox`, or a zero tool/write budget) must be adjudicated in one of two tables — one that forces `supports_file_output = False`, one recording that it was checked and still writes. A new flag nobody classified fails by name, so the question is answered when the flag is introduced rather than when a user's fan-out dies on it. **An argv guard is blind to a *default*, which is how `gemini` sat at `True` with a clean argv until it was measured**, so a further table sits beside those two: `NO_WRITE_TOOL_AT_ALL`, keyed by provider rather than by atom, whose rows are measurements naming their probe rather than opinions, and which feeds the same derived-roster assertion.
- **Usage is reported or absent, never zero** (`parse_usage`, D3j): claude-code reads the `result` envelope `parse_output` discards, codex the terminal `turn.completed` event, opencode the **sum** of every `step_finish` part (reading the last step alone under-reports a multi-step run). Every other adapter declares `usage: none` and records duration only; a batch mixing the two reports the partial sum plus `tasks_without_usage`.

## Common Pitfalls

- Use `--project` not `--directory` with `uv run` (path duplication bug)
- Never redefine a cross-cutting flag locally: `--host`, `--yes`/`-y`/`--non-interactive`, `--interactive`/`-i`, `--detach`, `--exec-subagents`, `--skip-prerequisites` come from `cli_common.build_parent_parser()`. Adding one to an orchestrator parser that already includes the parent raises `argparse.ArgumentError` at import of the parser, not at first use.
- A new mode is a row in `modes.py`, never an edit in twelve places — but the `argument-hint` **trailer** (everything after the mode alternation) is a literal, so a mode that introduces a new *flag* still needs that constant updated. Regenerate `tests/golden/*_help.txt` whenever the shared parent's help text changes.
- Group IDs are 16-char hex content hashes — use `state_manager.py` hashing, don't generate random IDs
- All output paths are plan-relative for portability
- Validation statuses: `valid`, `invalid`, `needs-human-decision`, `validation_failed`
- Importance levels: HIGH > MEDIUM > LOW
- **Grouping tracks meaning, not word count (2026-09-11).** `suggestion_processor.compute_similarity` is `0.33·title + 0.53·body + 0.08·reference + 0.02·type + 0.04·title-rarity` over normalized tokens (inline code spans tokenized like prose — a backticked identifier is the most specific thing a reviewer names — camelCase/dotted identifiers split, stopwords and review boilerplate removed, suffix-stemmed) weighted by IDF over the set being grouped — which is what demotes a plan's own subject word without a per-project stopword list; the reference channel is scaled by section rarity (a flat bonus handed every pair inside the review's biggest section the full 0.08, exactly where the near-threshold false pairs live), the title-rarity channel is the IDF mass of shared title tokens above `TITLE_RARITY_FLOOR` and is inert on small sets by construction, and two findings naming different files never merge (path-suffix aware; a file is evidence of difference only). `group_similar_suggestions` is agglomerative average-link (merge the closest pair, average over all cross pairs, stop at `DEFAULT_SIMILARITY_THRESHOLD` 0.20 — the safe band on the 2026-09-13 review is 0.196–0.205; below it a third finding joins a coherent pair, above it one comes apart), so it is order-independent by construction and cannot chain. The misses that remain on that review are structural, not tuning: a pair whose members each prefer a different neighbour cannot land in one group under average-link without the chaining the design rejects. A group's `theme` is `summarize_theme` (60-char budget, word-boundary cut, `…` only when cut) but `state_manager.generate_group_id` hashes the theme at the legacy 50-character cut, so a display change is not an identity change and the container goldens' baked ids hold. The old `0.3·title + 0.5·desc + 0.2·(type match)` bag-of-words with greedy single-link at 0.4 was uncorrelated with meaning: on a real 56-suggestion review it filed "activation semantics undefined" with two opponent-parity findings (the 0.2 type bonus was half the threshold) while nine obvious clusters stayed split across 23 groups; the new rules give 28 coherent groups where it gave 46. Every e2e fixture groups to byte-identical `group_hash` lists under both, so no golden moved. `html_report_generator.split_section_refs` files a group under every section a member cites — a composite `reference` such as `## Design Requirements / ### 7. Lap Integration` is split on a delimited ` / ` or `, ` (a bare slash is part of a heading), so per-section counts no longer under-report.
- Reaggregation globs `{phase_dir}/*.json` and treats each file as a per-model result list. Non-model JSON files written into a phase dir (e.g. `report_data.json`, `subagent_batch_report.json`, `state`, `.status`) MUST be added to every `exclude_patterns` list (`review_orchestrator_base.py` — two sites — and `code_review_orchestrator.py`) or they get parsed as suggestions and crash reaggregate. The executor's per-attempt diagnostics escape this by living in a **directory** (`{phase}/failed/`), which the glob never matches. Detach's artifacts are invisible to it by construction — `.status.json` because `glob` skips leading-dot names, `orchestrator-run.log` and its rotated `orchestrator-run.<run_id>.log` siblings by extension — and a regression test in `tests/test_status_file.py` pins that rather than assuming it.
- **Nothing durable stores a skill-dir-absolute command.** The plugin cache is keyed by commit hash, so the skill dir moves on every update. `{phase}/.status.json` records `reaggregate_mode` + `plan_file` + `replay_flags` (`cli_common.durable_reaggregate_fields` — the caller's selection flags as a *list*, never a resolved panel and never a command string) and readers rebuild the command from the *running* skill dir through `cli_common.retry_command` (`detach.resolved_reaggregate_command`, which is what `status --view run` prints). A stored flag list is spliced back verbatim, never validated against today's parser: dropping an unrecognized `--quick` is how a retry widens to `defaults.models`. Printing a resolved path is fine — it is session-scoped; persisting one is not. Both places the review base prepares validation tasks pass `orchestrator=<the phase's own script>`: the fan-out call omitted it (measured 2026-09-14), `prepare_batched_validation_tasks` defaulted to review-plan's, and a failed review-tasks run told the session model to re-invoke `review-plan --reaggregate`.
- **Adding a decision point without its flag is a review error.** A new gate needs a row in `utils/unattended.ROWS` (site id, modes, disposition, where it is enforced), a `DECISION_FLAGS` entry whose parser really accepts it, the resolution written into `instructions/full-workflow.md` *and* the mode file, and — if it auto-resolves — a `record_resolution` call. `tests/test_unattended.py` asserts all four; `tests/test_unattended_e2e.py` then re-runs every standalone mode under `--yes` with **stdin at /dev/null, no TTY and `gum`/`fzf` replaced by tripwires**, so "zero prompts" is observed rather than inferred from the absence of an `AskUserQuestion` string.
- `generate_html_report` persists `{phase_dir}/report_data.json` (the assembled report data) so the apply phase can overlay human/Claude decisions onto it and re-embed via `html_report_generator.py regenerate-decisions` — no reconstruction of runtime inputs (diff_data, base_ref, models). `regenerate-decisions --apply-phase` accepts either an apply phase's mode word or its `phase_name` (`html_report_generator._APPLY_PHASE_STATE_KEYS` normalizes `apply-code-fixes` → `apply-fixes`, the one apply phase where they differ), matching `state.json`'s `human_decisions_{phase_name}` key the orchestrator actually writes. `regenerate_report_with_human_decisions` returns `(report_path, matched)`, not just the path (F2, 2026-09-16): a report whose groups carry no `groupHash` (the code-review main path used to hand the validators and the merge step an un-stamped copy of `grouped` instead of the `stamp_stable_ids`-stamped `grouped_list`) used to overlay decisions onto nothing and report success anyway; both callers now print matched-vs-read and warn when they differ. `output_handler.PHASE_DIRECTORIES` and `utils/prior_changes.PHASE_ALIASES` carry the same `apply-code-fixes` → `apply-fixes` mapping so `status --phase`/`--abort`/`--sweep` and `prior_changes.jsonl`'s `append`/`render` resolve either spelling to the one phase (F1/F6, 2026-09-16) — `full_workflow_orchestrator.WRITE_PHASE_DIRS` was previously the only place that held it.
- **`code-review`'s `report.md` numbers ISSUES; every checkbox on it acts on a GROUP** (F1/F5, 2026-09-16). `generate_review_report` is the one report generator that iterates raw issues, so a consensus finding is rendered once per model — and `apply_code_fixes_orchestrator` used to index `self.groups` with those `### N.` numbers: measured on a 12-issue / 9-group review, 11 of 12 `- [x] Skip` / `Mark valid` / `Mark invalid` / `Let Claude decide` marks landed on a different finding and the last three fell off the end of the group list unreported — the user suppresses one fix and silently suppresses another while the one they meant still runs. Both sites (`parse_skips_from_report`, `apply_group_validation_overrides`) now resolve through `_group_hash_for_issue` → the `issue_to_group_map` `post_load_hook` already builds for the edited-description path, match `self.merged` by `group_hash` rather than by position (so `--resume`'s filtered list cannot re-key them either), warn instead of dropping a number the map cannot place, and take `invalid > needs-human-decision > valid > claude_decide` when two members of one group are marked differently. Without issues.json the legacy 1:1 reading survives, which is correct only when no two models agreed. The report says so rather than leaving it to be inferred: a `**Groups:** N` header line beside `**Total Issues:**`, `(of N groups)` on the validation line, `_Same finding as #7, #11 (3 models agree); marking any marks all._` on every member of a multi-member group, and `(group verdict)` on the badge those members share — counting the rendered badges used to give 10 Valid / 1 Invalid / 1 Needs Review over a 7/1/1 validation line and a 12-issue header, three sets of numbers none of which reconciled without `grouped.json`. The numbering itself does not move: `build_issue_to_group_map` and the parser's `### N.`-plus-next-line contract both depend on it — and that contract is now enforced from both ends (F6, 2026-09-16): `_format_issue` flattens newlines out of the title (a `\n` in one pushed the Skip box off the header line and lost the tick silently), and `report_parser` accepts a header only at column 0 after a blank line or the `---` rule, so a rendered description containing its own `### 2.` plus a ticked box cannot forge a skip on an issue the user never touched.
- **A provider log describes the invocation's final outcome, and names its provider.** `llm_client._save_log` writes `<PROVIDER> LOG` from the spec's provider prefix (`CLAUDE-CODE LOG`, `CURSOR-AGENT LOG`, …) with `Success:`/`Error:` for the outcome the caller actually got, plus `Result source: file|file_extracted|stdout_fallback` and, when the stdout extractor lost, either `Stdout parse: failed (<reason>)` (a real double failure) or `Stdout: not used (file output)` when `result_source` is one of `FILE_WRITTEN_SOURCES` — a file-output provider was told not to print JSON on stdout at all, so its failed stdout parse is expected, not a fault worth flagging beside `Success: True` (F9.2, 2026-09-16). `invoke_with_file_output` defers every exit-0 write, not only a parse failure (`_defer_parse_failure_log` → `details["_deferred_log"]`), and writes once, after the file-vs-stdout channel is resolved, via `_finalize_file_output_log` — until 2026-09-11 a claude-code review that completed through the file channel with 24 suggestions logged `Success: False` / `No valid JSON found in text` under a header that called it cursor-agent; until F13 (2026-09-16) a *clean* stdout parse wrote its log immediately, before the channel was known, so `Result source:` was silently absent for exactly the runs that used the stdout fallback. Hard failures (timeout, non-zero exit, launch failure) still write immediately — no channel choice to wait for. The per-model fan-out's `Output file: <path> (source: …)` line (`llm_client.describe_output_file`) only says "Output file" when `source` is `file`/`file_extracted`; a `stdout_fallback` source — the model never wrote there — says "Result will be saved to" instead (F14). The `save_agent_log` that once lived in `review_orchestrator_base` had no callers and is gone.
