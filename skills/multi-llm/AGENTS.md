# Multi-LLM Skill — Development Guide

## Architecture

- Orchestrators produce JSON instructions for Claude Code to execute — they never modify code directly
- **`multi_llm.py` is the single entrypoint.** Every mode is `uv run --project <skill-dir> -- python <skill-dir>/multi_llm.py <mode> [<positional>…] [--host <id>] [mode flags…]`, so a host shim resolves one path once and routes nothing itself. `<mode>` is a bare word and must be `argv[1]`; unknown/missing is exit 3 listing the valid modes. Positionals are normalized into the flags the target already parses (plan modes `<plan>`→`--plan-file`; `ask` `<plan> <question>`→`--plan-file` + `--question`, falling back to a dispatcher-written `--question-file` past `MAX_ARGV_QUESTION_CHARS`); an extra positional is exit 3. Everything after the positionals is forwarded **verbatim as a Python list** to that mode's `main(argv) -> int`, imported lazily and called **in-process — never `subprocess`** (one `uv` resolution per invocation, a plan path with a space survives by construction, `shlex` never runs on this path). `multi_llm.py <mode> --help` prints the target parser's help. Exit codes are uniform and never remapped: `0` done, `1` unexpected error, `2` nothing to do / phase already complete, `3` needs a human. Every invocation ends with exactly one machine-readable stdout line, `MULTI_LLM_RESULT: {"mode","phase","state","exit","artifacts":[…],"next":…}`, emitted even on a crash (`next` is `null` when no follow-up is owed).
- **`modes.py` is the one owner of the mode table** — mode words, the closed alias table (`review`→`review-plan`, `code-review`→`review-code`, `tasks`→`generate-tasks`; no prefix or fuzzy matching), positionals, lazy dispatch targets, phase names, core instruction files, and which modes are user-facing. `SKILL.md`'s `argument-hint`, `multi_llm.py --help` and `check_workflow_prerequisites.py`'s `--mode`/`--phase` choices are all **rendered** from it; adding a mode is a row, and `tests/test_instruction_portability.py` fails if the dispatcher and `argument-hint` disagree. Note the one place mode word ≠ phase name: mode `review-code`, phase `code-review`.
- **`utils/cli_common.py`** owns the cross-cutting argparse **parent** (`--host`, `--yes`/`-y`/`--non-interactive`, `--interactive`/`-i`, `--detach`, `--if-not-running`, `--max-detached N`, `--exec-subagents`, `--skip-prerequisites`, plus the suppressed `--internal-worker`/`--internal-run-id` re-entry flags), included by every `*_orchestrator.py` parser plus `check_workflow_prerequisites.py` and `init_config.py`, so a direct invocation accepts the same flags with the same semantics. It also owns skill-dir resolution — `os.path.abspath`, **symlinks preserved, never `realpath`** (`link-skill.sh` symlinks the plugin cache at a dev checkout; resolving would move `uv run --project` off the `pyproject.toml` the host loaded) — plus the printed-command builders, the `MULTI_LLM_RESULT` emitter and the per-invocation record (mode word + normalized argv) a detached child re-executes. `--exec-subagents` is implemented for the **read/analyze** phases (below); `--detach` is implemented for the fan-out modes (below).
- **`--detach` self-daemonizes the fan-out modes** (`review-plan`, `review-tasks`, `review-code`, `ask` — the only long-running ones until the executor lands; every other mode exits 3 rather than accepting a flag that does nothing). One boundary crossing, `utils/review_orchestrator_base.maybe_detach`, sits *after* all pre-flight (flags, inputs, model resolution, phase-dir creation, lock pre-check) and *before* any model runs, so a bad flag or an unconfigured provider fails on the caller's terminal with **no child and no log**. The invoker forks (POSIX: `setsid` + a second fork, so the worker reparents to init and the invoker has no child to reap; Windows: `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` with the log handed in as stdout/stderr), waits ≤10 s for the worker to publish its own identity, then prints the log path plus the `status`/`--abort` commands. The child re-executes `uv run --project <skill-dir> -- python <skill-dir>/multi_llm.py <mode> … --internal-worker` — **never bare `python`** (`sys.executable` inside `uv run` loses the lockfile and `--project`) — with `--detach`'s implications (`--yes`) written out and paths absolute. `--detach` implies `--yes` and is exit 3 with `--interactive` at parse time. Never combine it with a host's own background primitive: Claude Code uses `run_in_background` and never passes `--detach`.
- **`{phase}/.status.json` is one file with one schema**: today's checkpoint plus two reserved objects, `run` (the process machine `starting → running → {done, failed, aborted}`, heartbeat, pid + `process_start_time` identity, `exit_code`, `error`, `resolutions`) and `progress` (display only). `run.state` is **not** the top-level `state` (the phase machine resume reads) — a crashed fan-out is both. Primitives live in `utils/status_file.py` (re-exported by `review_orchestrator_base` as `write_status`/`update_status`, so nothing about the write path changed) because `status` must stay sub-second; `run`/`progress` merge key-by-key like `output_files`, a plain `write_status` cannot erase them, and every write after the worker's initial claim is **compare-and-set on `run_id`** so a closed-out run can never resurrect itself. Liveness is the heartbeat (10 s; expired at 60 s = six missed beats); `{phase}/.lock` (`utils/process_control.py`: `flock`/`msvcrt`, held on an open fd) makes one writer per phase dir, and a second run against a live holder is exit 3 naming it. Every run ends in exactly one terminal state with `run.exit_code` recorded — the worker records its own (nothing is its parent after the double spawn), and `status` closes out `failed(heartbeat_timeout)` with `exit_code: null` when the heartbeat expires and the identity probe says the process is gone.
- **`utils/unattended.py` owns the unattended contract (D6): fifteen decision *sites*, three dispositions, no questions.** `ROWS` is the closed table — each site keyed by a stable `site_id`, the modes that reach it, the disposition it lands on (**auto-select** / **fail closed** / **explicit flag** — "ask in free text" is not a fourth option) and where it is enforced; `DECISION_FLAGS` is the D5a input contract, one flag per row whose values enumerate exactly what a question would have rendered. **Exit 3 is reserved across every mode for "unattended run cannot proceed"** (missing uv, unmet prerequisite, contradictory or empty decision flag), distinct from the exit-2 phase-already-complete guard, so a host can tell "needs a human" from "already done". `validate_decision_flags(argv)` runs in the dispatcher *before* any parser so `--models ""`, `--human-task <id>=` and an unknown `--force-strategy` are exit **3** at parse time rather than argparse's exit 2; `choices` on each parser is the second layer. `record_resolution(phase_dir, site_id, decision)` prints `[AUTO_RESOLVED] <site>: <decision>` and, under `--detach`, appends to `run.resolutions` via `detach.record_resolution` → `status_file.append_resolution` (a foreground `.status.json` still gains no new keys). Auto-resolutions are announced only under `--yes`, so with `--yes` unset a run is byte-for-byte what it was. `--yes` also now *implies* `--claude-decide` in every apply phase (`apply_orchestrator_base.apply_unattended_defaults`) and resolves the human-task strategy to `skip-dependents`; it **never** implies `--skip-prerequisites`.
- **Python never sniffs its host (D6b).** No `isatty()`, no `CI=` read, no `--print` detection: interactivity is *requested* (`--interactive`), never detected, so the same argv produces the same phases in a terminal and in a pipe. `utils/interactive.is_tty()` is gone and `resolve_models(..., unattended=True)` never reaches a picker — it returns `defaults.models` or raises `NeedsHuman` (exit 3). `full-workflow.md`'s "no TTY → skip review-tasks" branch is deleted. `tests/test_unattended.py` parses every runtime module's AST (so a *comment* about `isatty` is not a call) and fails any reintroduction; the one allowlisted `isatty` is `utils/metrics.py`'s ANSI-colour gate, which decides how a line looks and never which phases run. `--yes` with `--interactive` is exit 3, never precedence.
- **The prerequisite gates are the one place `--yes` must not be generous (D6a).** `check_workflow_prerequisites.py` owns rows 5/6/13 — no thin orchestrator, no gate logic in markdown. Standalone + `--yes` = exit 3 with one `[PREREQUISITE_UNMET]` block naming *both* fixes (apply first, or `--skip-prerequisites`) in absolute paths and D5a-shaped commands; `--skip-prerequisites` = `[PREREQUISITE_SKIPPED]` + a recorded skip through the same `--skip --reason` state path (surfacing downstream as one `[PREREQUISITE_SKIPPED_UPSTREAM …]` line, never re-asked); inside the workflow, `ensure_prerequisites(..., in_workflow=True, apply_runner=…)` runs the missing apply phase **once** and re-checks — a second unmet re-check is exit 3, not a retry. Nothing is produced before the gate. `ensure_prerequisites` is **callable but not yet called in production**: the Phase-3 full-workflow orchestrator is its intended caller and must inject `apply_runner` (applying suggestions needs the agent's subagent channel); with no runner, workflow mode behaves like standalone. **Streams:** this script's stdout stays pure JSON (callers `json.loads` all of it) and its `[PREREQUISITE_*]` blocks go to stderr + the JSON's `message`; `implement_orchestrator.py`, whose stdout is already prose+markers, prints its own on stdout.
- **The uv bootstrap is split across three layers (D6c), and the wording lives in `hosts/uv-missing.txt`.** `install-host --check` (install time) and each rendered shim's `command -v uv` preflight (invocation time — the only host-side logic that cannot be Python) are D7's; the **Python backstop** is `unattended.require_uv()`, run by the dispatcher before every mode for the cases the first two cannot cover (uv removed after install, a host calling `multi_llm.py` directly, a hand-edited shim). Same message, same exit 3, never an install, and **no `python3 -m` fallback ever** — dependencies are pinned in `uv.lock`, so a bare interpreter turns "install uv" into a `ModuleNotFoundError` or a silently wrong version mid-fan-out. `references/uv-check.md` is the shim-side contract and points at the message file; `utils/detach.resolve_uv()` keeps its own narrower probe for the worker re-exec (same `$MULTI_LLM_UV` override).
- **`utils/process_control.py` is the only place `fcntl`/`msvcrt`/`ctypes` process internals appear** (locking, liveness, creation-time identity, process-group/Job Object teardown, the detached spawn). It is the façade `plans/windows-macos-portability.md` owns; per that plan's sequencing rule this work typed it first, so its signatures are a cross-plan interface. A test fails any other runtime module that imports `fcntl` or `msvcrt`.
- **`util` namespace, not a user-facing surface**: `multi_llm.py util metrics|prior-changes|report|decisions|update-tasks|prereq|backup|runs|instructions …` routes the utility scripts the same in-process `main(argv)` way, flags forwarded verbatim. Excluded from `argument-hint` and from `--help`'s mode list, documented only under `multi_llm.py util --help`, and — like the reserved hidden `--internal-*` prefix — never rendered into a `MULTI_LLM_RESULT.next` value. `util instructions <mode>` prints a mode's core instruction file with every skill-dir placeholder replaced by the running skill dir, so the text a host agent reads carries no unexpanded token.
- **Import must be side-effect free.** Every dispatch target keeps argparse and all work inside `main(argv)`, with `if __name__ == "__main__": sys.exit(main(sys.argv[1:]))` — no module-level argparse, no module-level `sys.argv` read, no I/O at import. Two targets can run in one interpreter, and `tests/test_instruction_portability.py` enforces it (AST guard + a one-process import probe). Direct invocation of `*_orchestrator.py` stays **supported but unadvertised** (the test suite and `--internal-*` re-entry rely on it); the instruction core and shims name only `multi_llm.py`.
- `generate-tasks` and `full` are dispatchable but exit 3 with "not yet available on this host" until `generate_tasks_orchestrator.py` / `full_workflow_orchestrator.py` land; `install-host`/`uninstall-host` likewise. `init` is a thin wrapper forwarding to `init_config.main` (narrative in `instructions/`).
- **`status <plan>` is a real command (`utils/run_status.py`), not the retired instruction-only `--status` mode**: one word, two named views over two files, never merged. `--view workflow` reads `state.json` through `check_workflow_prerequisites.get_workflow_status` and is **byte-identical** to `check_workflow_prerequisites.py --status` (which survives unchanged as that view's implementation); `--view run` reads `{phase}/.status.json`; `--view all` (default) prints both as labeled sections, two keys under `--json`. Three state fields — workflow phase, in-phase `state`, `run.state` — print on three lines and are never collapsed, and a finished run under an unmarked phase is reported as the normal post-run condition, not a conflict. Selectors: `--phase` (mode word *or* phase name, resolved through `modes.py`), `--question`, `--run-id`, `--all`. Exit codes follow the run view and **are** the poll-loop condition: `0` terminal-done, `2` non-terminal (including "no run recorded" — never `0`), `3` terminal-needs-human, `1` unreadable. It takes no lock and writes nothing, so it works while another run owns the dir; its one write is the deliberate `failed(heartbeat_timeout)` close-out. `--wait` (default 90 s, under OpenCode's ~120 s cap) compresses the loop into one turn; hosts must never spell the wait as `sleep <n>; status` in one shell call. `--abort` (alias `abort`/`cancel`/`stop <plan>`) is the **only** kill path — identity probe → process-group SIGTERM → 10 s → SIGKILL → `run.state: aborted`, idempotent (exit 2 when nothing was running). `--sweep` closes out orphans under a plan; `util runs [--sweep]` does it across the `{project_root}/.multi-llm/runs/` registry, which also enforces the `MULTI_LLM_MAX_DETACHED` (default 4) ceiling.
- **Printed follow-up commands are fully resolved, never placeholders** (`code_review_orchestrator.py`'s two sites, `utils/validation.py`'s `reaggregate_command`): they compute absolute paths from `__file__` and are built via `cli_common.reaggregate_command*`. Two rules bind them: the **allow-rule prefix is part of the contract** — the command must still start with `uv run …` / `PYTHONUNBUFFERED=1 uv …` or it stops matching Claude Code's `Bash(uv:*)` glob and every follow-up becomes a permission prompt — and printed commands **carry their own assertions**, because the golden regression bundle compares phase artifacts and never stdout. An absolute skill-dir path is safe to *print* (session-scoped) and never safe to *persist*: the Claude plugin cache is keyed by commit hash.
- **Config layering** (`provider_registry.load_config`): base `providers.yaml` → auto-discovered `<git-root>/.multi-llm/providers.yaml` → `MULTI_LLM_PROVIDERS_CONFIG` env override. The auto-discovered layer deep-merges its **full** contents — including a `providers:` block — over base, identical to the env layer (no longer filtered to selection keys). Deep-merge, lists replace, `None` skipped. Discovery anchors on the optional `anchor` (plan path threaded from `resolve_models`) then CWD; cache keyed on the resolved anchor. Present-but-invalid explicit overrides fail fast (`ConfigError`); `MULTI_LLM_PROVIDERS_CONFIG_PERMISSIVE=1` restores warn-and-skip. Config `command` is metadata-only and NEVER executed (binaries are hardcoded in `utils/providers/`); a merged provider name with no hardcoded adapter is ignored at runtime. Scaffold via `init_config.py` (`--init`, auto-detects installed CLIs). **`driver:` is the fourth top-level block** (`subagent_runner`, `subagent_runner_cheap`, `max_concurrent_subagents`, `subagent_timeout_s`, `subagent_retries`), fully populated in base so nothing has to guess, read only through the typed accessors (`get_driver_config`, `get_subagent_runner`, `get_subagent_timeout`, `get_max_concurrent_subagents`, `get_subagent_retries`, `get_driver_provenance`) and never by indexing `config["driver"]`. Validation is fail-fast and only for an **explicit override layer**: an unknown key under `driver:` is rejected rather than ignored (a typo is not a silent no-op), a runner spec must be an explicit `provider:model` whose provider has a built-in adapter — **raising, where the fan-out path warns-and-filters**, because a filtered runner degrades to "no runner configured" and resurfaces mid-phase. The `--init` template carries the same block fully commented (byte-diffed against base by CI, so a base default change forces a regeneration).
- **Materialized subagent tasks are the one delegation contract.** Every task file an orchestrator emits (`validation_tasks.json`, `revalidation_tasks.json`, `consolidation_tasks.json`, `salvage_task_<model>.json`, `human_decision_tasks.json`) carries `tasks_schema_version: 2` and, per task, a complete `prompt` plus `output_name`/`output_path`, `result_channel: file`, `context_mode`, `capability_tier`, `executor_role`, `task_id` and an `inputs` hash block — validated against `schemas/subagent_tasks.schema.json` **on write and on read** (`utils/subagent_tasks.py`). The invoker's whole job is: run `task.prompt` as a subagent, write the JSON it returns to `task.output_path`; the callee only prints. Prompt bodies live in `utils/subagent_prompts.py` as five **pure** generators (no I/O, no clock, no config — identical inputs render byte-identical text, pinned by `tests/golden/prompts/`), never in instruction markdown. **No generator interpolates `plan_file`, `grouped_file` or `output_path` into prompt text**: under `context_mode: inline` every input travels inside `prompt`, because a headless runner is not guaranteed a workspace-read tool. A v1 file, or one whose `inputs` hashes have moved, is refused with **exit 3** naming the phase dir — prompts are derived data, so the fix is always re-materializing (`--force`), never patching. `executor_role` (`agent`|`human`) is the routing field every reader branches on; `subagent_type` is optional Claude-only metadata that no reader consults and the schema rejects when it disagrees. Judge verdicts are files (`human_decision_batch_<n>.json`, `schemas/human_decision_verdicts.schema.json`) ingested by `utils/human_decisions.py`, never chat text.
- **`utils/subagent_executor.py` is the second invoker of those task files (`--exec-subagents`, D3 read/analyze half).** One dispatch is: refuse before spawning (the D2 refusals plus containment) → pick a **profile from the task kind**, never from the task JSON (`agent-readonly` for every read/analyze kind, `cwd` pinned to the repo) → capture stdout → the adapter's **`parse_output` first, then `json_extractor`** (provider CLIs emit event streams; raw extraction would match an envelope or a reasoning item and write a garbage result reaggregation would accept) → validate against the kind's result shape → atomic 0600 write under the phase dir. `persist_result` is the **shared** invoker-persists leg: `simulate_native_invoker` (which `SkillRunner.simulate_subagents` delegates to) calls the same function, which is what makes "either invoker, byte-identical `output_path`" a property of the code. Every failure lands on exactly one **D3k rung** (`spawn_failed`/`auth_failed` 1, `timeout` 2, `rate_limited` 3, `runner_error` 4, `unparseable_result` 5, `schema_invalid` 6, `rejected` 7); rungs 2/4/5 consume `driver.subagent_retries`, rate limiting backs off **without** consuming it, rungs 6/7 are never retried, and rung 1 fails the whole batch. Each failed attempt writes `{phase}/failed/{task_id}.attemptN.json` with the prompt elided to its sha256. A batch with any failed or incomplete task writes `{phase}/subagent_batch_report.json`, refuses to reaggregate and exits **3 even under `--yes`** — and **never** falls back to salvage. Resume is defined by artifacts: a task is done iff its `output_name` exists, parses and validates, so re-invoking a phase re-dispatches exactly the failed set. `run_tasks_concurrent` (`utils/review_orchestrator_base.py`) is `run_models_concurrent`'s mechanics keyed by `task_id` instead of `model_spec` — same global gate, same per-provider semaphores, same stagger — because a subagent batch normally shares one runner and a model-keyed map would overwrite completed tasks.
- **`--exec-subagents` continues past markers in-process (D3b)**, via `review_orchestrator_base.dispatch_subagent_tasks`: markers are still printed (logs, `.status.json`) but are informational, and the phase finishes in one invocation — validation and revalidation into their merges, judging into `record_human_decision` and the apply set, consolidation into `reaggregate_consolidation_mode`, salvage into the repaired model-result file. With the flag **off** every one of those sites returns `False` and behaves byte-for-byte as before; salvage dispatch is deliberately non-fatal (a failed salvage leaves that model failed, which the D6 row-3 partial-results path already covers).
- `ask` mode (`ask_orchestrator.py`) is a read-only free-text Q&A side-channel: markdown output, no JSON schema / grouping / validation, output under `{plan}/ask/<question-slug>-<hash8>/`. It shares concurrency mechanics with the review modes via `run_models_concurrent` in `review_orchestrator_base.py`.

## Developer Notes

- **Full model for validation**: Validation subagents use full model capability — never downgrade to haiku. Only the coordinator (simple orchestration) uses haiku.
- **Backup before modification**: Always backup files before any salvage or modification operation.
- **A read/analyze dispatch never gets write access.** An adapter opts into `agent-readonly` by implementing `build_agent_command(prompt, model, profile)` with the runner's **own** denial mechanism (codex `--sandbox read-only`, opencode `--agent plan`, claude `--allowed-tools`/`--disallowed-tools`) and declaring it in `agent_profiles`. There is no fabricated read-only mode: an adapter without one raises `ProfileUnsupported` and is refused as a runner with the reason named. `tests/test_providers.py` (and `tests/test_subagent_executor.py`) cross-check declaration against implementation in both directions, for profiles **and** for `parse_usage`/`usage_support`, so the capability data cannot drift from the code.
- **Usage is reported or absent, never zero** (`parse_usage`, D3j): claude-code reads the `result` envelope `parse_output` discards, codex the terminal `turn.completed` event, opencode the **sum** of every `step_finish` part (reading the last step alone under-reports a multi-step run). Every other adapter declares `usage: none` and records duration only; a batch mixing the two reports the partial sum plus `tasks_without_usage`.

## Common Pitfalls

- Use `--project` not `--directory` with `uv run` (path duplication bug)
- Never redefine a cross-cutting flag locally: `--host`, `--yes`/`-y`/`--non-interactive`, `--interactive`/`-i`, `--detach`, `--exec-subagents`, `--skip-prerequisites` come from `cli_common.build_parent_parser()`. Adding one to an orchestrator parser that already includes the parent raises `argparse.ArgumentError` at import of the parser, not at first use.
- A new mode is a row in `modes.py`, never an edit in twelve places — but the `argument-hint` **trailer** (everything after the mode alternation) is a literal, so a mode that introduces a new *flag* still needs that constant updated. Regenerate `tests/golden/*_help.txt` whenever the shared parent's help text changes.
- Group IDs are 16-char hex content hashes — use `state_manager.py` hashing, don't generate random IDs
- All output paths are plan-relative for portability
- Validation statuses: `valid`, `invalid`, `needs-human-decision`, `validation_failed`
- Importance levels: HIGH > MEDIUM > LOW
- Reaggregation globs `{phase_dir}/*.json` and treats each file as a per-model result list. Non-model JSON files written into a phase dir (e.g. `report_data.json`, `subagent_batch_report.json`, `state`, `.status`) MUST be added to every `exclude_patterns` list (`review_orchestrator_base.py` — two sites — and `code_review_orchestrator.py`) or they get parsed as suggestions and crash reaggregate. The executor's per-attempt diagnostics escape this by living in a **directory** (`{phase}/failed/`), which the glob never matches. Detach's artifacts are invisible to it by construction — `.status.json` because `glob` skips leading-dot names, `orchestrator-run.log` and its rotated `orchestrator-run.<run_id>.log` siblings by extension — and a regression test in `tests/test_status_file.py` pins that rather than assuming it.
- **Nothing durable stores a skill-dir-absolute command.** The plugin cache is keyed by commit hash, so the skill dir moves on every update. `{phase}/.status.json` records `reaggregate_mode` + `plan_file` (`cli_common.durable_reaggregate_fields`) and readers rebuild the command from the *running* skill dir (`detach.resolved_reaggregate_command`, which is what `status --view run` prints). Printing a resolved path is fine — it is session-scoped; persisting one is not.
- **Adding a decision point without its flag is a review error.** A new gate needs a row in `utils/unattended.ROWS` (site id, modes, disposition, where it is enforced), a `DECISION_FLAGS` entry whose parser really accepts it, the resolution written into `instructions/full-workflow.md` *and* the mode file, and — if it auto-resolves — a `record_resolution` call. `tests/test_unattended.py` asserts all four; `tests/test_unattended_e2e.py` then re-runs every standalone mode under `--yes` with **stdin at /dev/null, no TTY and `gum`/`fzf` replaced by tripwires**, so "zero prompts" is observed rather than inferred from the absence of an `AskUserQuestion` string.
- `generate_html_report` persists `{phase_dir}/report_data.json` (the assembled report data) so the apply phase can overlay human/Claude decisions onto it and re-embed via `html_report_generator.py regenerate-decisions` — no reconstruction of runtime inputs (diff_data, base_ref, models).

```bash
uv run --project skills/multi-llm -- pytest
uv run --project skills/multi-llm -- pytest tests/test_filtering.py -v
uv run --project skills/multi-llm -- pytest -m robustness
```
